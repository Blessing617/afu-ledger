# 变更：账单识别准确率、信息完整性、功耗与无感化

## 动机

用户在小米 14 Pro（HyperOS / Android 16）上真实使用了一整天，遇到五类问题。每一条都在真机上取到了具体证据，不是猜测。

**1. 识别错误（金额/方向/误触发）**

在真机上采了支付宝 20 张、微信 20 张真实账单详情页，发现四个独立的成因：

- **方向被抹掉**：支付宝账单详情页无障碍文本里的金额是 `支出25元` / `支出29.74元`
  （视觉上是 `-25.00`，文本里是中文口语），方向信息就在「支出」两个字上。
  而 `AmountParser` 对所有结果统一 `.abs()`，`RecordDetectedPaymentUseCase`
  又把 `type` 硬编码成 `EXPENSE` —— 入账账单必然被记成支出。
- **加号不认**：微信红包收入页的金额文本是 `+128.50`，而 `bareAmountPattern`
  是 `^-?(?:...)\.\d{2}$`，**不接受前导 `+`**，`symbolPattern` 要 `¥`、
  `yuanPattern` 要「元」 —— 三条路全不匹配，红包收入直接 `NO_AMOUNT` 漏记。
- **多金额即放弃**：支付宝「扫经营码付款」详情页同时有
  `订单金额 17500.00`（原价）、`某银行立减金 -0.22`（优惠）、
  `支出17499.78元`（真实金额）。现有实现判 `AMBIGUOUS_AMOUNT` 直接放弃，
  这类页面**永远记不上账**。
- **主界面误触发**：排除逻辑靠「主界面专有入口词」计数凑阈值，
  词表覆盖不到的二级页（如各类「更多」页、活动页）就会带着页面里的历史金额文案通过。

**2. 信息不全（尤其「昨天的账单记在今天」）**

`PaymentDraft` 里只有 `capturedAt = System.currentTimeMillis()`，也就是**识别时刻**；
`RecordDetectedPaymentUseCase` 直接拿它当 `occurredAt` 写库。
账单上的时间字段**从来没有被解析**（`TradeNoExtractor` 之外没有时间提取器）。

而真实账单页的时间字段至少有四种标签：`支付时间`（微信/支付宝）、
`收款时间`（微信红包）、`创建时间`（支付宝退款页）、`交易时间`。
只要账单不是当天点的，记账日期就必然错。

同一批样本还暴露了另外三处信息缺口：

- **交易单号取不到**：支付宝账单详情页的「交易单号」折叠在「更多」里，
  默认不渲染 —— 采到的 20 张支付宝账单**没有一张**带单号。
  于是指纹退化成「包名+金额+商户+日期」，去重能力大幅下降。
- **商户取的是邻近文本**：微信详情页顶部是列表名（「美团」），
  真实商户在 `商品` 字段里（`满香客（金桥店）-美团App-...`）。
- **页面自带分类没被用**：支付宝详情页有 `账单分类 餐饮美食`，微信有交易类型，
  现在全部忽略，一律落到默认分类。

**3. 续航（开着耗电发热）**

这一条的严重程度比「有点耗电」高一个量级：**用户为了省电，已经自己把无障碍服务关掉了**
（真机实测确认：设备的 `enabled_accessibility_services` 里只剩李跳跳，
本应用的自动记账服务不在其中）。也就是说这个功能目前处于被用户主动停用的状态 ——
不解决功耗，其余四项改进根本用不上。

具体来源：
- 无障碍配置 XML **没有声明 `packageNames`**，全系统的每个无障碍事件都会回调进本服务；
- 订阅了 `typeWindowContentChanged`（滚动、动画都会触发，是事件量最大的一类）；
- 同时开了 `flagIncludeNotImportantViews` 与 `flagRetrieveInteractiveWindows`，
  节点树更大，且要遍历**所有**窗口；
- `onAccessibilityEvent` 里每个事件都执行 `pendingJob?.cancel()` +
  `scope.launch { }`，在微信/支付宝里滚动时每秒几十次协程创建与取消。

**4. 无感化（无障碍图标碍事）**

服务配置里声明了 `flagRequestAccessibilityButton`。这个 flag 除保活收益外，
副作用正是让系统显示**无障碍快捷按钮/图标** —— 也就是用户看到那个碍事的图标。

**5. 识别速度**

微信账单页整页 OCR（30 行量级）每次都要走完整推理。而用户真正在意的只有
「点进账单 → 弹出确认」这段，其中绝大部分时间花在读根本用不到的下半屏。

## 范围

在范围内：

- **识别范围收敛为「账单详情页」**：主界面、我的页、列表页、支付结果页一律不识别。
  支付结果页识别本期**关掉**（保留代码不删，默认不参与判定），后续再开。
- 金额语义：识别「支出/收入/入账/退款」方向，落到 `TransType`；金额文本支持
  `支出25元`、`+128.50`、`-23.90`、`100元` 四种形态。
- 账单时间：解析 `支付时间 / 收款时间 / 创建时间 / 交易时间`，
  入账用账单时间而不是识别时间。
- 字段补全：交易单号（含「更多」展开后的读取）、真实商户、页面自带分类向账本分类的映射。
- 排除非交易金额：`订单金额 / 原价 / 优惠 / 立减金 / 余额 / 状态栏读数`。
- 功耗：包名白名单、事件类型收敛、协程复用、息屏零工作。
- 无感：去掉无障碍图标，通知降打扰。
- 速度：微信通道两段式 OCR（先上半屏快筛，命中再整页提字段）。
- **回归测试样本集**：把采到的 40 张真实账单固化成可自动跑的测试数据。

不在范围内：

- 支付结果页 / 聊天页 / 通知栏的识别（明确推迟到后续变更）
- 自动展开「更多」以外的页面交互（不模拟点击其他控件）
- 多账本、云同步、导入导出
- 数据库 schema 变更（若需新字段优先走 DataStore / 现有列复用）
- 新的分类体系设计（只做「页面分类 → 账本分类」的映射表）

## 方法

1. **把「页面文本」升级为「带位置的字段视图」**：`PageSnapshot` 不再只是一串文本行，
   而是能按「标签 → 值」取字段的行+坐标结构。金额、时间、单号、商户、分类全部
   走同一套字段提取，不再各自写一套「邻近猜测」。
2. **金额解析引入方向与优先级**：先按「支出/收入」前缀（支付宝）、正负号（微信）
   定方向，再按标签优先级挑金额，最后才做歧义放弃。排除词表从「余额」扩展到
   「订单金额/原价/优惠/立减金」。
3. **新增 `BillTimeExtractor`**：解析四种时间标签，产出 `occurredAt`；
   解析失败时回退为识别时刻，并在日志里标明是回退。
4. **判定顺序固定为**：包名白名单 → 页面类型（必须是账单详情页）→ 方向 → 金额唯一 → 字段提取。
   支付结果页不再作为命中类型。
5. **功耗**：XML 里声明 `packageNames` 白名单（debug 版另加自家包名）；
   事件处理改成「一个常驻判定循环 + 时间戳」，不再每事件创建协程；
   `retrieveInteractiveWindows` 与 `includeNotImportantViews` 逐项评估保留价值。
6. **无感**：去掉 `flagRequestAccessibilityButton`，用前台服务 + JobScheduler 巡检
   承担保活；常驻通知保持 `IMPORTANCE_LOW` 且可关闭。
7. **速度**：微信通道先对上半屏做一次 OCR，只有命中「账单详情」特征才做整页；
   注意这与既有「禁止 det+rec 两阶段」约束不冲突 —— 用的是同一个整页模型，只是裁剪区域不同。
8. **测试**：`test/bill-samples/` 存原始截图与（支付宝的）无障碍树；
   从中导出文本行 fixture 到 `app/src/test/resources/bills/`，单测直接喂 `PaymentPageDetector`。
