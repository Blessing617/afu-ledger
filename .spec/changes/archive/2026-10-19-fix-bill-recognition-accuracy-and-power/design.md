# 设计：账单识别准确率、信息完整性、功耗与无感化

## 1. 从「文本行列表」升级为「字段视图」

### 问题

现在整条链路都是 `List<String>` + 各种「邻近猜测」：

- `AmountParser` 猜哪个数字是金额
- `MerchantExtractor` 取金额前后两行当商户
- `TradeNoExtractor` 扫标签后面的数字
- 没有任何时间提取器

字段之间没有关系，于是每加一个字段就要再写一套猜测，且互相不知道对方在猜什么。

### 方案

`PageSnapshot` 保留文本行（OCR 与节点两个通道都产出它），但新增一层**字段视图**：

```
data class BillFields(
    val amountText: String?,      // 原文，保留方向信息
    val direction: Direction?,    // EXPENSE / INCOME / null（判不出）
    val occurredAt: Long?,        // 账单时间
    val occurredAtSource: TimeSource,  // PAGE / FALLBACK
    val merchant: String?,
    val tradeNo: String?,
    val pageCategory: String?,
    val evidence: PageEvidence,   // 命中了哪些强证据，用于日志
)
```

它由一组**字段提取器**协同产出，而不是各自为政：

- `BillFieldParser` 是唯一的入口：先把文本行整理成「标签 → 值」对（同一行冒号后、
  或同一视觉行的左右两列），再分别交给金额/时间/商户/分类提取器。
- 「标签 → 值」是账单页的天然结构：支付宝是「支付时间 / 值」，微信是
  「当前状态 / 支付成功」两列。用结构取字段，比按位置猜稳得多。
- 只有在结构取不到时，才退回现有的邻近猜测（作为兜底，不是主路径）。

### 坐标是必需的，不能只有文本

真机导出的树暴露了一个必须处理的事实：**节点树的顺序不等于视觉顺序**。

```
top=1071 left=451  2026-10-19 18:01:22     ← 值，top 反而更小
top=1078 left= 91  支付时间                 ← 标签
```

同一个视觉行里，右侧的值节点 top 比左侧的标签**小 7px**。只按 top 排序，
扁平列表里就成了「值在前、标签在后」，`支付时间` 后面跟的是下一行的内容。

因此：

- `PageSnapshot` 的每一项 MUST 携带 `top` / `left`，而不只是字符串；
- 「标签 → 值」的还原 MUST 先按 **top 容差（±20px）分组为视觉行**，
  行内再按 left 排序；同一行内「A B」两段天然就是「标签 值」；
- OCR 通道的行本身已经是一段文本，把它当作「只有一个元素的视觉行」参与同一套逻辑。

→ 这条同时决定了 fixture 的格式：导出的 JSON 必须带坐标，
否则测试里还原不出真机上的行结构（已按此导出）。

**取舍**：为什么不直接改成纯正则全集？因为微信账单页的节点不可读，只能靠 OCR，
而 OCR 的行顺序在跨列布局下不可靠（「当前状态」和「支付成功」可能被切成同一行或错序）。
保留「标签→值」+ 同一行多列的拆分规则，能同时兼容节点与 OCR 两种顺序。

## 2. 金额与方向

### 顺序

```
parseAmount(texts) -> (Money, Direction?)?
  ① 带方向前缀的行：支出/付款 → EXPENSE；收入/入账/收款/退款 → INCOME
     取该行里的数字；命中即返回
  ② 整行即金额的行（^-?\d+\.\d{2}$ 或 ^\+\d+\.\d{2}$）：符号定方向
  ③ 其余带 ¥ / 元 的行，符号定方向，方向可空
  ④ 排除非交易金额（余额 / 状态栏 / 订单金额 / 优惠 / 立减金）后，
     若只剩一个候选则返回；多个则返回歧义
  ⑤ 方向仍为空时，用页面状态词补（退款→收入，支付成功→支出）
  ⑥ 方向仍为空 → 放弃本次识别
```

`+` 必须被接受：现有 `bareAmountPattern` 的 `^-?` 是漏掉红包收入的直接原因。

### 为什么「带方向前缀的金额」优先

支付宝在无障碍文本里把金额口语化成 `支出17499.78元`，这一行同时**携带了方向**，
是页面上语义最强的一处。其他数字（订单金额、立减金）没有方向，天然是次级。
用「有方向的优先于没方向的」来定夺，比扩充排除词表更稳 —— 改版后新出现的
原价字段不会立刻让识别失效。

## 3. 时间

新增 `BillTimeExtractor`：

- 标签集：`支付时间`、`收款时间`、`交易时间`、`创建时间`、`转账时间`
- 格式：`yyyy-MM-dd HH:mm[:ss]`、`yyyy年M月d日 HH:mm[:ss]`
- 允许标签与值分两行（OCR 常见）
- 解析失败 → `TimeSource.FALLBACK`，用识别时刻，并在日志里标注

**取舍**：为什么不从「列表页那条记录」取时间？因为我们只在详情页识别 ——
这正是「只识别账单页」带来的简洁性。列表页的「今天 18:01」这种相对时间还要额外
处理跨日，而详情页永远有绝对时间。

## 4. 功耗

按收益从大到小：

| 措施 | 收益 | 风险 |
|---|---|---|
| XML 声明 `packageNames` 白名单 | **最大**：系统侧就不把其他应用的事件送进进程 | 注释里提到「部分 ROM 对 XML 包名过滤行为不一致」 |
| 不订阅无关事件类型 | 中：减少回调 | 需确认换页信号仍够用 |
| 事件处理不创建协程/对象 | 中：滚动时消除分配压力 | 需重写去抖实现 |
| 息屏/锁屏短路 | 小但确定 | 无 |
| `includeNotImportantViews` / `retrieveInteractiveWindows` | **不动** | 参考项目 GKD 也保留它们（见第 5 节），砍掉会读不到 H5 文本 |

**packageNames 的取舍**：现状是为了「debug 构建能测自家模拟页」和「担心 ROM 行为不一致」
而完全不限定。这是把「测试便利」和「防御性猜测」放在了真实功耗之上。

改法（两层）：

1. **静态**：`res/xml/` 声明最小白名单（微信、支付宝）；debug 的模拟页需求由
   `src/debug/res/xml/` 覆盖一份多一个自身包名的配置解决，不让 release 承担全量事件。
2. **动态**：`AccessibilityServiceInfo` 的 `packageNames` / `eventTypes` /
   `notificationTimeout` 都是**可在运行时改写**的字段，用 `setServiceInfo()` 生效。
   于是「白名单」不必在编译期写死：跟随设置页里用户开启的识别来源动态收窄，
   也顺手解决了「某个 ROM 不遵守 XML 过滤」的兜底 —— 运行时再设一次。

即便两层都失效，代码里还有第三道 `isSupportedPackage` 校验，不会产生错误识别。

**协程风暴**：现状是每个事件 `pendingJob?.cancel()` + `scope.launch{}`。
改成：

```
private val debounceAt = AtomicLong(0)
private val scheduler = 单一常驻协程（或 Handler 的单条消息）
onAccessibilityEvent: 只更新时间戳与标志位，必要时 post 一次
```

用一个 `Handler` 的 `removeCallbacks/postDelayed` 即可，零对象分配（复用 Runnable 实例）。

## 5. 无感化

### 图标从哪来（先分清是哪个图标）

「碍事的无障碍图标」可能有三个来源，处理方式完全不同：

| 来源 | 由谁控制 | 能否去掉 |
|---|---|---|
| 系统无障碍按钮（导航栏方块/边缘悬浮） | `FLAG_REQUEST_ACCESSIBILITY_BUTTON` 请求，系统渲染 | **能**，去掉 flag |
| 状态栏的系统「无障碍已启用」小图标 | HyperOS/MIUI 系统行为，任何无障碍服务开启都会出现 | **不能**，与应用代码无关 |
| 本应用的前台服务常驻通知图标 | 应用自己 | **能**，降低重要性或允许隐藏 |

本应用当前声明了 `flagRequestAccessibilityButton`，因此第一项确实在发生。

### 参考项目怎么做的

看了 **GKD**（`gkd-kit/gkd`，用户量最大的开源无障碍工具之一）的实际配置
（`gkd-android/src/main/res/xml/a11y_info.xml`）：

```xml
android:accessibilityFlags="flagReportViewIds|flagIncludeNotImportantViews|flagDefault|flagRetrieveInteractiveWindows"
android:isAccessibilityTool="@bool/is_accessibility_tool"
android:notificationTimeout="100"
```

三点结论：

1. **它没有声明 `flagRequestAccessibilityButton`** —— 说明「不要图标」和「长期稳定运行」
   在真实用户量下是可以同时成立的，保活并不依赖这个 flag。
2. 它**保留了** `flagIncludeNotImportantViews` 与 `flagRetrieveInteractiveWindows`，
   说明这两个 flag 对「读到 H5 / WebView 里的文本」是必要的，本应用不该盲目去掉
   （这笔开销要靠包名白名单和事件降频来省，而不是砍掉读文本的能力）。
3. 它显式声明了 **`android:isAccessibilityTool`**，本应用没有。这是 Android 12+
   用来声明「本服务是辅助工具而非滥用无障碍」的属性，加上它对系统行为和被判定为
   恶意软件的风险都有好处。

### 决定

- **去掉 `flagRequestAccessibilityButton`**（与 GKD、李跳跳一致）；保留另外两个读取类 flag。
- **补上 `android:isAccessibilityTool="true"`**。
- 保活按第 11.2 节的优先级重构：前台服务（`specialUse`）+ `AccessibilityWatcher`
  实时监听撤销 + **回到应用时把服务写回启用列表**（可选 `WRITE_SECURE_SETTINGS`，
  设置页给可复制的 adb 命令）+ 周期巡检降级为增强。
- 状态栏那个系统级无障碍小图标**无法由应用关闭**，设置页要如实说明这一点，
  避免用户以为是我们没做无感。

**取舍**：牺牲的是 AOSP `onPackagesForceStoppedLocked` 里被归入 `continuousServices`
的那一点恢复优势。GKD 在没有这个 flag 的情况下依然被大量用户长期使用，说明该优势
并非决定性；而图标是用户每天都会看到的持续干扰。

### 通知

保持 `IMPORTANCE_LOW` + 无声无振动无角标。额外：用户可在设置里隐藏常驻通知
（隐藏后失效提醒仍然保留，因为那是独立通道）。

## 6. 速度：微信两段式 OCR

微信账单页的关键字段全部集中在**上半屏**（实测四类样本）：

| 字段 | 位置（占屏高） |
|---|---|
| 商户名 | 18–22% |
| 金额 | 25–30% |
| 当前状态 | 37–39% |
| 支付/收款时间 | 42–45% |
| 交易单号 | 48–55% |

因此快筛区取 **上 60%**，一次 OCR 就能判断「是不是账单页」并取到全部关键字段。
命中后再按需处理其余区域（目前其余区域只有「账单服务」按钮，没有记账所需字段，
所以实际上多数情况下快筛就够了）。

**与既有约束的关系**：主规格禁止的是「先检测文本框、再逐行识别」的两阶段方案
（成本随行的宽度总和线性增长）。这里是**同一个整页模型**作用于不同裁剪区域，
不引入第二次检测，因此不冲突。

**风险控制**：快筛覆盖率必须由样本集验证 —— 新增 Requirement 要求「快筛区域覆盖所有
已知账单类型的关键字段」，回归测试里对每条样本断言快筛区能取到金额与时间。

## 7. 判定顺序

```
① 包名白名单（运行时二次校验）
② 页面准入：必须是账单详情页（标题 或 ≥2 个专属字段）
   —— 负向排除词表只做辅助，不再是主防线
③ 金额与方向
④ 字段提取（时间 / 商户 / 单号 / 分类）
⑤ 去重指纹（单号优先，退化用账单时间）
⑥ 弹窗
```

支付结果页不再参与判定：`classifyPage` 里删掉 `resultKeywords` 分支
（代码保留但返回 null，后续变更再启用）。

## 8. 不模拟点击

支付宝的交易单号在「更多」里。**不做自动展开**：

- 点别人的界面属于越界操作，用户会看到页面自己动
- 展开后页面变化又会触发新一轮事件，形成正反馈
- 退化指纹（包名+金额+方向+商户+账单时间）已经足够区分同一商户的多笔

## 9. 测试策略

- 支付宝样本 → 从 XML 按坐标顺序导出文本行 → 直接喂 `PaymentPageDetector`
- 微信样本 → 只有截图。**导出脚本必须带一次 OCR**：用 App 自身的 ML Kit 引擎跑
  （在真机上通过 debug 构建导出），或离线跑一次把结果存成文本。
  在本变更里，微信 fixture 允许由人工从截图录入关键行，但 MUST 标注来源为 `OCR`，
  并允许后续用真实 OCR 覆盖替换。
- 负样本：支付宝首页、支付宝「我的」页、微信钱包页、微信账单列表页 ——
  这些的文本行同样导出成 fixture，断言「未命中」。

## 10. 已决策的三个取舍

1. **退款记成收入**（用户确认）：支付宝退款页有「退款成功 / 100元 / 账单分类 退款」，
   入账为一笔收入 100 元。不做「冲减原支出」——那需要关联原账单，而原账单我们可能
   根本没记过，找不到冲减对象时行为不可预期。悬浮窗上能改方向/分类兜住个别情况。
2. **已全额退款的账单照常按支出记录**（用户确认）：钱确实付出去过；
   与之配对的退款单会以收入出现，一进一出互相抵消。
3. **去掉无障碍图标，改用 GKD 同款配置**（用户要求「看别的项目怎么做再决定」）：
   见第 5 节。GKD 的实际配置证明「不要图标」与「长期稳定运行」可以并存。

## 11. 调研推翻或修正的两处原设计

### 11.1 悬浮窗可能根本弹不出来（钱迹/iCost 的公开失效边界）

钱迹官方 FAQ 明确写了：微信支付成功页必须**退出界面**才弹窗；云闪付的支付/账单页
完全不弹窗，要退到后台才行。原因是部分系统对支付类 App 有「支付保护」，
禁止在其上显示悬浮窗。iCost 也说明「自动弹出仅支持部分软件」，未支持的走控制中心调用。

这直接威胁本变更的核心假设：**识别成功 ≠ 用户看到卡片**。
如果只在识别成功的那一刻弹窗，遇到支付保护就等于静默丢账。

修正：把**识别**与**展示**解耦。

- 识别成功后先落成一条「待确认账单」（内存 + DataStore，带指纹与 TTL），
  再尝试弹窗；
- 弹窗失败（`addView` 抛异常或窗口不可见）时，MUST 退化到可用的提示通道：
  常驻通知上的待确认计数、或应用内首页的「待确认」入口；
- 用户下次进入本应用时，待确认列表必须能继续处理，不能因为当时没弹成而丢。

这条同时解决了「用户划走了卡片 / 当时没空」的现实情况。

### 11.2 保活真正缺的不是周期巡检，而是「回到 App 时自愈」

调研的四个实现（钱迹、iCost、李跳跳、AutoAccounting）里，
**JobScheduler 周期巡检一个都没有**。钱迹的做法最直接：

- 申请 `WRITE_SECURE_SETTINGS`（一条 `adb` 命令，之后不必再开 USB 调试）；
- 在「打开钱迹 / 回到主页 / 下拉快捷设置」这些时机**尝试把无障碍服务写回启用列表**；
- 但用户在 App 内主动关掉自动记账时不会自动打开（尊重用户意图）。

真正被系统杀掉的是**无障碍开关**，而不是我们的进程 —— 所以巡检进程意义有限，
在用户回到 App 的那一刻修复开关才是刚需。

修正：保活手段按此优先级排：

1. 前台服务（specialUse）—— 进程优先级；
2. `AccessibilityManager` 监听授权撤销，实时告警（已有 `AccessibilityWatcher`）；
3. **应用启动 / 回到前台时自愈**：检测服务未在启用列表就尝试写回（需要
   `WRITE_SECURE_SETTINGS`，设置页提供一条可复制的 adb 命令）—— 无权限时退化为提示；
4. 周期巡检（`AccessibilityGuardWorker`）降级为「可选增强」，不再是主手段。

## 12. 外部参考与它们的取舍

逐条对照，避免「闷头乱搞」：

**钱迹自动记账**（[官方说明](https://docs.qianjiapp.com/auto/qianji_auto_android.html)）
—— 对外承诺三条：「只识别与支付相关的页面内容」「离线算法」「最小权限」；
权限清单是无障碍 + 通知 + 悬浮窗。FAQ 里同时公开了失效边界（支付保护禁止弹窗、
淘宝主动屏蔽无障碍、发红包要再点开红包、微信双开触发不稳）。
→ 本变更「正向准入 + 只认账单详情页」与它同路；它的失效边界被吸收成 11.1 的解耦设计。
它的「忽略电池优化是必选项」与本变更的引导项一致。

**iCost 智能记账**（[官方说明](https://help.icostapp.com/guide/ai/ai_android.html)）
—— 用户旅程是「进入**账单详情页面** → 自动识别并弹出记账窗口」，
未支持的软件提供控制中心调用。
→ 印证「只在账单详情页识别」是这个品类的标准做法，不是我们独有的妥协。

**AutoAccounting**（`AutoAccountingOrg/AutoAccounting`）
—— 规则是**数据**（`RuleModel` 存 JS，分 `system` / `user`，可启停，按 `(app, DataType)`
分组，`DataType` 只有 `OCR / DATA / NOTICE` 三值）；命中第一个 `money > 0` 的规则即止。
分类是完全独立的一层 `getCategory(money, type, shopName, shopNameSanitized, time, ruleName)`，
**入库前跑一次、去重合并后对父账单再跑一次**，且强制用「清洗后的商户名」匹配
（洗掉金额、6 位以上订单号残余）。
去重是两级：入口 MD5（60s TTL）+ 账单级（金额 + 时间 ±300s + 方向），
命中后**不删除子账单**而是记 `groupId` 合并，合并按「更具体者胜」而不是「后到者胜」。
→ 可借鉴：① 分类映射表必须吃清洗后的商户名（本变更第 3 节已按此写）；
② 指纹去重的时间窗思路可用在「同一账单被重复打开」的场景；
③ 规则做成数据、能不发版更新 —— 本期不做，但把 `PaymentPageRules` /
映射表集中成一处、可单测，就是为将来数据化留的口子。
→ 不借鉴：多来源交叉验证需要 Xposed 与网络，与本项目「无 INTERNET、纯无障碍」冲突；
且它两个仓库的 hook/规则实现大部分闭源，抄不到字段规则，只能抄架构分层。

**GKD**（`gkd-kit/gkd`）
—— 无障碍配置见第 5 节，是「不要图标也能长期稳定运行」最直接的证据。
它的 `a11y_info.xml` 里 `accessibilityFlags` 不含 `FLAG_REQUEST_ACCESSIBILITY_BUTTON`，
但保留了 `flagIncludeNotImportantViews` 与 `flagRetrieveInteractiveWindows` ——
说明这两个读取类 flag 是必要的，不能为了省电砍掉。
另外它提供了通过 Shizuku 提权、用 UiAutomation 替代无障碍服务的路径。
→ 本期不引入：Shizuku 要求用户额外安装授权，收益（连系统状态栏图标都没有）
对当前价值不高。仓库已有 `ShizukuGuard.kt`，将来要「彻底无痕」可从这条路径演进。

**李跳跳**
—— 逆向资料显示它的配置是 `accessibilityFlags="flagDefault"`，**同样没有请求无障碍按钮**；
它以「安静、不要权限之外的任何东西」为卖点。
→ 它的存在本身说明：无障碍类工具的用户预期就是**不可见**，本变更按同一标准要求自己。

**其他同赛道开源实现的配置对照**
—— 有实现把 `packageNames` 限制到 4 个包并配 `notificationTimeout="500"`，
其 XML 注释直言「不限制的话系统每次界面变化都会喊我们，手机立刻变卡、电也哗哗掉」；
另一个实现列了 21 个包（含电商、拨号盘），说明白名单要与服务职责一致。
→ 支持本变更把 `packageNames` 作为最省电的单点改动。
