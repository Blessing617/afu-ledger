# 真实账单页实测记录

在Android 16 真机 上用**真实的微信 / 支付宝页面**做的端到端测试。
此前主要用内置模拟页（5 行文本）验证，与真实页面差距极大 —— 这个变更的全部值都来自真实页面。

## 一、最终结果

| 场景 | 文本来源 | 耗时 | 识别结果 |
|---|---|---|---|
| 微信账单详情（30 行） | 截图 OCR | **283 / 320 / 346 / 398 ms** | ✅ 金额正确 |
| 支付宝 H5 账单详情（31–33 行） | 截图 OCR | **373 / 399 ms** | ✅ 金额正确 |
| 支付宝付款成功页 | 无障碍节点 | 走节点，不截图 | ✅ 金额正确 |
| 微信账单详情 | 截图 OCR | 1204 ms（改前） | 金额正确但慢 |

**`OCR 处理耗时 ≤ 400ms` 目标达成**（稳态 283–399ms）。

识别结果抽样：

```
微信：ocr lines=30 in 320ms → hit amount=2680 merchant=阿佑鲜烫牛內米线
微信：ocr lines=29 in 366ms → hit amount=2680 merchant=阿佑鲜烫牛內米线
支付宝：ocr lines=33 in 399ms → hit amount=2500 merchant=(取到商品说明碎片)
```

金额全部正确。商户名在支付宝 H5 页会取到商品说明的换行碎片（见「已知不足」）。

## 二、根因：为什么原来那么慢

原实现用 **PP-OCRv4，det + 逐行 rec 两阶段**。真实微信账单详情页有 30 行文本，
于是要做 1 次 det + 30 次 rec：

```
ocr lines=30 in 1450ms (capture=92 det=148 rec=1159)
ocr lines=31 in 1877ms (capture=83 det=390 rec=1294)
```

`det` 与 `capture` 加起来只有 240–480ms，**`rec` 独占 69%**。

### 关键测量：rec 成本由「宽度总和」决定，与批次数无关

把 30 行的宽度与耗时对齐后：

| 批次 | 行数 | 宽度 | 耗时 |
|---|---|---|---|
| 1 | 4 | 40–49 | 36 ms |
| 2 | 1 | 51 | 11 ms |
| 3 | 4 | 80–86 | 51 ms |
| 4 | 11 | 141–169 | 256 ms |
| 5 | 2 | 237–246 | 62 ms |
| 6 | 2 | 306–316 | 80 ms |
| 7 | 3 | 391–485 | 201 ms |
| 8 | 1 | 511 | 62 ms |
| 9 | 3 | 639–640 | 271 ms |

宽度总和 7460 单位 × 0.14ms ≈ 1044ms，与实测吻合。
**单位成本恒定 ⇒ 批量不省时间**，把 9 批合成 1 大批反而更慢（窄行被 pad 到最宽）。

### 验证过的无效优化

| 尝试 | 结果 |
|---|---|
| 把所有行拼成一个大批（pad 到最宽） | 5 行场景 **557ms → 709ms**（变慢） |
| 按宽度分档批量（容差 25%） | 分成 9 档，与逐行几乎无差别 |
| 预过滤状态栏 + 长单号 | 只过滤掉 2 行，rec 无改善 |
| 缩小 rec 输入宽度上限 | 省不到 5% |

## 三、真正的解法：换掉两阶段引擎

同赛道的 Tally（`cypressincloud/Tally`）用的是 **Google ML Kit 中文文字识别**：
`TextRecognition.getClient(ChineseTextRecognizerOptions())`。

```java
// Tally 的 ScreenshotOcrHelper.java
Text text = Tasks.await(recognizer.process(InputImage.fromBitmap(bitmap, 0)));
```

**整页一次前向推理，没有「逐行」这个阶段。** 这是两者最本质的差别。

| | PP-OCRv4 | ML Kit |
|---|---|---|
| 流程 | det 找框 + 逐行 rec（30 行 = 31 次推理） | 整页 1 次推理 |
| 30 行耗时 | 1450–2204 ms | **283–399 ms** |
| 模型 | 16MB（onnxruntime） | 约 14MB（随 APK 打包） |
| 离线 | ✅ | ✅ 不触网，保持「无 INTERNET 权限」 |
| 输出结构 | 需自己拼框、排序、NMS | 直接给 lines + boundingBox |

改造后删掉了 `PpOcrEngine` / `CtcDecoder` / `DbPostProcessor` / `OcrImageOps` /
`BitmapScaler` / `OcrModelInstaller` 与 `assets/ocr/` 下的 16MB 模型。
APK 从 41MB → **35MB**（debug）。

## 四、顺带修掉的三个真实缺陷

### 缺陷 1：支付宝 H5 页面「有金额却永远不识别」

日志：`miss NO_AMOUNT`

支付宝的账单详情、余额明细详情是 **H5**，内容区不暴露无障碍节点。
整个无障碍树里只有 3 个节点：

```
返回
(空)
余额明细详情
```

而原逻辑是「节点文本 ≥3 行就采信节点、不再看 OCR」。这 3 行正好凑够，
于是 OCR 被短路，金额永远读不到。

**修复**：判据从「行数够」改为「行数够 **且** 字符数 ≥ 20」；
并且节点路径判定失败时，只要 OCR 可用就**再兜底试一次 OCR**。
另外 `shouldUseOcr` 原本写死「支付宝永不截图」，改为按受支持包名放行
（调用顺序保证只在节点不可靠时才会走到）。

### 缺陷 2：支付宝金额歧义（余额被当成交易金额）

日志：`miss AMBIGUOUS_AMOUNT`

支付宝「余额明细详情」页 OCR 出 33 行，其中三个像金额：

```
5.24        ← 状态栏网速（单位 KB/s 被切到相邻行）
-25.00      ← 真正的交易金额
¥217.01     ← 账户余额（上一行是「余额」）
```

三个都被解析 → 判为歧义 → 整页放弃。**页面明明有金额，却永远不记账。**

**修复**：新增 `AmountParser.parseTransactionAmounts`，**只做排除不做挑选**：
- 本行或前后**两行**内出现「余额 / 可用余额 / 账户余额」→ 该金额不是交易金额
- 前后两行内出现 `KB/s`、`℃` 等单位 → 状态栏读数

排除后若仍有多个不同金额，**依然放弃**（守住「宁可漏记也不记错」的底线）。
这一点与 Tally 不同：Tally 是多金额时按评分选一个，我们刻意不采纳。

> 踩坑：第一版只看 ±1 行。真实微信状态栏被切成 `0.11` / `0:07` / `KB/s` 三行，
> 网速值的相邻行是时间、单位在隔一行处，于是 `0.11` 没被排除，
> 和 `-26.80` 一起构成歧义，**微信反而识别不了了**。改为 ±2 行后正常。

> 踩坑 2：「余额宝」是支付方式，不是余额。按「含余额」判断会把
> 「支付方式 余额宝」的相邻金额（也就是本次支付金额）误丢，
> 表现为付款成功页识别不到金额。已在判断前先剔除「余额宝」。

### 缺陷 3：支付宝首页把搜索框文字当成商户名

日志：`hit amount=2500 merchant=公积金查询`

支付宝首页「最近消息」区列出历史通知文本（「天猫 / 付款成功 / ¥25.00」），
节点可读 → 命中支付特征词 → 弹窗，商户名取到了搜索框占位文字。

**修复**：新增 `mainScreenKeywords`（扫一扫 / 收付款 / 卡包 / 市民中心 / 余额宝 / 通讯录 / 发现），
命中 ≥3 个判定为主界面，不识别。

> 踩坑：第一版词表里放了「更多」「出行」「转账」，阈值取 2 ——
> 结果**支付宝账单页也识别不了了**，因为这些词在账单页同样常见。
> 改为「只在主界面出现的专有入口」+ 阈值 3 后解决。

## 五、已知不足

- **支付宝 H5 页的商户名不准**：会取到商品说明的换行碎片
  （如「钥家庭升级工作站」）。金额正确，商户名可由用户在确认卡片上修改。
  根因是长商品名被 OCR 切成多行，碎片恰好紧邻金额行。
- **账单列表页不识别**（`miss MAIN_SCREEN` / `NOT_PAYMENT_PAGE`）：这是预期行为，
  列表页不是支付结果，不应弹窗。
- 支付宝账单详情页的「查看账单详情」是嵌套入口，其标题为「账单详情」，
  与「余额明细详情」是两种页面，两者现在都能识别。

## 六、引入 ML Kit 带进来的网络权限（已移除）

替换引擎后 `aapt2 dump permissions` 立刻发现多了两条权限：

```
uses-permission: name='android.permission.INTERNET'
uses-permission: name='android.permission.ACCESS_NETWORK_STATE'
```

来源是 ML Kit（以及 WorkManager）的库 Manifest —— 库会把权限合并进最终 APK。
这直接违反本项目「不申请任何网络能力」的硬约束。

**修复**：在 `AndroidManifest.xml` 用 `tools:node="remove"` 强制移除这两条，
并在注释里写明理由（bundled 模型不触网；万一库内部尝试联网，
拿到的 `SecurityException` 会被 `runCatching` 吞掉，不影响离线识别）。

**验证**：移除后重新核对权限列表，无任何网络相关权限；并在真机上确认

```
ocr channel ready (mlkit)
ocr lines=32 in 350ms → hit amount=2390 merchant=美团
```

即**无网络权限下 ML Kit 中文识别完全正常**。

> 这也是一个流程教训：换依赖后要重新跑 `aapt2 dump permissions`，
> 不能只看自己写的 Manifest —— 权限是合并出来的。
