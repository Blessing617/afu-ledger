# 变更：把识别延迟做到目标值

## 动机

上一个变更（`fix-ui-motion-and-recognition-latency`）把微信截图 OCR 从 1894ms
降到 **557ms**，方向对了，但**没有达到规格写的 400ms**；
支付宝的「页面稳定 → 悬浮窗可见 ≤ 250ms」也没能取得可靠的真机数字。
这两条是本变更的全部内容。

不做的话，规格里写着的这两个预算就是空话 —— 而规格自己失真是这套流程最要避免的事。

## 范围

在范围内：

- 微信截图 OCR 从 557ms 压到 ≤ 400ms
- 真机测出支付宝节点通道的实际延迟，并压到 ≤ 250ms
- 首次启用 OCR 时，把「模型正在准备」暴露给用户，避免以为没反应

不在范围内：

- 更换或重训 OCR 模型（仍用 PP-OCRv4 移动版）
- 引入任何网络能力
- 改动金额解析、页面判定、去重语义

## 方法

557ms 的剩余开销主要在两处：rec 逐行串行推理（一屏 5 行就是 5 次推理）、
以及全屏 HardwareBuffer → ARGB_8888 的拷贝。前者可评估批量推理或按行裁剪，
后者可评估在缩放前就下采样。支付宝一侧需要先解决测试环境问题
（MIUI 会周期性覆盖无障碍授权），否则没有可信的对比数据。

## 现状记录

| 指标 | 当前 | 目标 |
|---|---|---|
| 微信截图 OCR 单次处理 | 557ms | ≤ 400ms |
| 支付宝页面稳定 → 可见 | 未取得可靠数字 | ≤ 250ms |
| 首次启用 OCR 的准备状态 | 无提示 | 有提示 |
