# 变更：无障碍自动记账（微信 / 支付宝支付结果页）

## 动机

v0.1.0 只能手动记账：每笔支出都要打开 App、填金额、选分类账户，付款后很容易忘。真实痛点是**付款那一瞬间金额和商户都在屏幕上，却要人再抄一遍**。

本次变更让 App 在付款完成后自己「看见」金额，用一个悬浮窗请用户确认后入账，把「记一笔」从二十秒压到一次点击。

硬约束（来自需求）：

- 不申请 `INTERNET` 权限，识别与入账全部在本机完成
- 目标机型Android 16 真机（Android 16 / HyperOS），需要真机端到端可用
- 只做无障碍单通道：不引入通知使用权、不引入截图 OCR、不读短信

## 范围

在范围内：

- 声明并实现一个可开关的无障碍服务，只读取微信、支付宝的支付结果页
- 从页面节点文本提取金额（必选）与商户名（尽力而为），金额统一转成「分」
- `TYPE_ACCESSIBILITY_OVERLAY` 悬浮窗确认：展示金额与商户名，可当场改账户与分类，确认才入账
- 同一笔支付去重，避免页面刷新导致重复弹窗或重复记账
- 设置页「自动记账」区块：总开关、默认账户、默认分类、识别日志开关与最近记录
- Android 16 真机 / Android 16 的授权引导与保活适配（受限设置、自启动、省电策略）

不在范围内（后续变更）：

- **通知监听通道**：银行工资到账、先用后付、红包到账、部分 App 的支付通知都依赖它
- **截图 OCR 通道**：微信部分页面是自绘的，拿不到文本节点时需要它
- **短信 / 银行推送通道**
- 微信、支付宝之外的页面适配（美团月付、抖音支付等自有收银台；仅当支付最终跳到微信/支付宝收银台时才顺带覆盖）
- 收入自动记账（本次只处理支出；红包、转账、工资到账均不自动识别）
- 自动分类（关键词库）；本次用默认分类 + 用户当场修改
- 「忽略一次 / 永不提示该商户」这类规则记忆
- 云同步、统计图表、周期记账

## 方法

新增一个独立能力 `auto-ledger`，与现有 `bookkeeping` 解耦：

- `AccessibilityService` 只负责「把当前窗口的文本节点交给识别器」，不做业务判断
- 识别与解析做成纯 Kotlin 层（规则表 + 金额解析 + 去重），可 JVM 单元测试
- 悬浮窗用 `TYPE_ACCESSIBILITY_OVERLAY`，不需要 `SYSTEM_ALERT_WINDOW`
- 确认后复用现有 `TransactionRepository` 写入，不新增写库路径
- 原始页面文本只在开启识别日志时短期保留在本地，默认不落库

参考实现（仅借鉴机制，不复制代码）：

- [blue-whale-keeper](https://github.com/a2244921700-code/blue-whale-keeper)：多通道证据融合、指纹 + 60 秒窗口去重、「未来时态不记账」的防误记思路
- [autoexpense-releases](https://github.com/Meggie6363/autoexpense-releases)：以「支付成功页」为触发点的页面识别划分

验收方式（不产生真实支付）：不要求真金白银付一笔。用**历史账单详情页**（微信/支付宝账单里点开旧交易）、**debug 内置模拟支付页**（复刻页面文案）+ **公开截图样本** 来验证识别、弹窗、入账、去重与超时。详见 design.md 的测试策略。

## 风险

- **微信自绘页面可能读不到文本节点**。识别不到时不弹窗（宁可漏记不误记），并写入识别日志；后续由 OCR 变更兜底。
- **微信 / 支付宝版本更新会改页面结构**。规则集中在一张表里，失效时改表即可，不散落在 Service 中。
- **HyperOS 对无障碍服务的限制**（侧载受限设置、后台清理）可能导致服务被停。需要引导页与真机验证，不能假设「开了就一直活着」。
