# Delta：auto-ledger

## MODIFIED Requirements

### Requirement: 主界面与列表页不触发识别
系统 SHALL 在判定页面不是**账单/支付页**时跳过识别。

判定 MUST 采用正向准入而不是负向排除：页面必须**同时**满足下列条件才允许识别：

- 命中账单详情页标题（`账单详情` / `交易详情` / `余额明细详情` / `账单明细` 等）
  **或**命中 ≥ 2 个账单专属字段（`交易单号` / `商户单号` / `收单机构` / `清算机构` /
  `支付时间` / `收款时间` / `账单分类` / `对方账户` / `商品说明` 等）
- 不命中列表页判据（≥3 行「日期+时间」、**≥3 行只有时分的时间**、或 ≥2 个列表页专有文案）
- 不命中主界面 / 我的页专有入口词的组合
- **不命中聊天 / 会话页判据**（见下）

**标题 MUST 是一条独立的标题行**，而不是页面上任何位置出现过这个词：
匹配时要求该行**以标题关键词开头**，且不带 `>` / `›` 这类跳转标记，且 MUST 只在页面前几行内匹配。
微信支付公众号会话里每条消费记录下面都挂一个「账单详情 >」链接，按「整页包含」来判，
整个会话页都会被当成账单详情页（真机事故：27.00 那笔就是这么弹出来的）。

**会话列表 MUST 被当成列表页排除**：微信会话列表每行右侧只有 `14:58` 这种时分、没有日期，
上面那条「日期+时间」判据抓不到。因此页面里出现 ≥3 行「只有时分的时间」时 MUST 判为列表页。
真机事故：会话列表里「微信支付 · 已支付¥27.00」那一行同时提供了状态词与金额，整页被当成支付结果页。

主界面与列表页的排除判据 MUST 保留，但只作为**辅助**：漏掉一个入口词时，
正向准入仍然能拦住误触发。MUST NOT 把「排除词表命中」当作唯一防线。

**聊天 / 会话页 MUST 是一级排除**，排在结果页判定与账单页准入**之前**：
把它放在结果页之后就会重演本次事故——聊天里的转账卡片自带「转账 / 已收款 / 已存入零钱」，
正好构成结果页证据，于是打开聊天界面就弹出一张金额完全不对的卡片。

判定 MUST 不依赖 OCR 的空格：匹配前 MUST 去掉文本中的所有空白字符，
因为「按住 说话」在 OCR 里可能读成「按住说话」「按住 说 话」。

聊天 / 会话页证据分两类：

- **输入栏类**：`按住说话`、`语音输入`、`发送消息`、`聊天信息`、`按住讲话`
- **聊天卡片 / 会话行为类**：`微信转账`、`微信红包`、`消息已发出`、`对方正在输入`、
  `撤回了一条消息`、`拍了拍`、`[动画表情]`、`转账给`

例外：`转账给` 这一类词在**真正的转账账单详情页**上也会出现。
因此命中「聊天卡片类」词时 MUST 再看一眼强字段：若页面同时命中 ≥ [MIN_BILL_FIELD_HITS]
个账单专属字段（含 `转账单号` / `当前状态` / `转账时间`），MUST 判定为账单页并继续识别；
否则 MUST 放弃。

MUST NOT 因为「页面里出现了金额」就认为可以识别：识别的前提是页面自证它是账单页 / 结果页，
金额只在准入通过之后才有意义。

**支付结果页 MUST 有「金额是全页字号峰值」这个结构证据。** 用 OCR 给出的行高判断：

- 金额行的高度 MUST ≥ 其它行里**最高那一行**高度的 1.2 倍（微信支付成功页的金额约是正文的两三倍）
  —— 用「最高行」而不是「中位数」：会话列表里状态栏那种小字会把中位数拉低，
  拿中位数比时列表正文的金额也能过关（真机实测）
- 拿不到行高信息时（无障碍节点通道、或 OCR 未给出高度）MUST 跳过这条判据，MUST NOT 因此否掉识别
- 判据 MUST 只用于**支付结果页**：账单详情页的准入由标题与强字段负责，不靠字号

这条是为真机事故补的：用户在微信里付了 27.00（正常弹窗并入账），随后点开与好友的聊天界面，
又弹出一张卡片，金额 2700。聊天正文里既没有「转账」也没有「已收款」，
词表拦不住；页面又缺少账单字段，于是被当成「支付结果页」放行。
但聊天页永远不具备「金额是全页最大的字」这个特征 —— 这是结构判据能挡住它的原因。

### Requirement: 无感化（无障碍图标与通知）
系统 MUST NOT 声明 `FLAG_REQUEST_ACCESSIBILITY_BUTTON`，因为它的副作用是在系统界面显示
无障碍快捷按钮/图标。用户明确要求界面上不出现该图标。

服务 MUST 在系统允许的版本上声明 `android:isAccessibilityTool="true"`，表明本服务是
真正的辅助工具用途（与 GKD 等成熟无障碍应用一致）。

保活 MUST 改用其余手段实现（前台服务、授权状态监听、周期巡检），
MUST NOT 因此退化为「静默失效」——失效可见性由既有 Requirement 保证。

状态栏上由系统绘制的「无障碍已启用」小图标不受应用控制，设置页 MUST 如实说明这一点，
MUST NOT 让用户误以为应用还有可关闭的图标没有关。

常驻通知 MUST 属于低打扰通道：不发声、不振动、不弹横幅、不显示角标，
且用户关闭通知权限时 MUST NOT 影响识别功能。

**常驻通知的文案 MUST 只有一句「阿福自动记账运行中」**：
标题用它，MUST NOT 再挂「识别微信 / 支付宝支付页，数据全部留在本机」这类副标题。
用户在通知栏里只需要知道「它在跑」，不需要读产品说明；副标题只会让常驻通知显得啰嗦。

#### Scenario: 开启后界面上没有无障碍图标
- GIVEN 用户开启了本应用的无障碍服务
- WHEN 返回桌面或任意应用
- THEN 屏幕边缘与导航栏不出现本应用的无障碍按钮/图标

#### Scenario: 常驻通知只有一句文案
- GIVEN 自动记账处于开启状态
- WHEN 下拉通知栏查看常驻通知
- THEN 通知只有「阿福自动记账运行中」这一行
- AND 不出现「识别微信 / 支付宝支付页」之类的副标题

#### Scenario: 通知不打扰
- GIVEN 自动记账处于开启状态
- WHEN 用户停留在任意应用
- THEN 常驻通知不发声、不振动、不弹横幅、不显示角标

#### Scenario: 关闭通知后仍能识别
- GIVEN 用户在系统设置里关闭了本应用的通知权限
- WHEN 用户停在账单详情页
- THEN 确认悬浮窗仍能正常出现
- AND 设置页提示「通知关闭后失效时收不到提醒」

### Requirement: 识别结果的可观测性扩展
系统 SHALL 在识别日志中记录足以复现判断的字段：方向、账单时间、以及「时间是否回退」标记、
本次使用的去重指纹，MUST NOT 记录完整页面原文。

**识别日志 MUST 落盘保存，进程重启后仍可查看。** 记录在应用私有存储里，环形保留最近
200 条 / 7 天，超出即淘汰；写盘 MUST NOT 阻塞识别主流程（丢了日志也不能拖慢弹窗）。
「昨天出现的好几笔重复」必须能在第二天还查得到，否则日志只剩排查价值为零的当下现场。

- 每条记录 MUST 至少包含：时间、来源应用、结果（弹窗可见 / 已入账 / 用户忽略 / 超时 / 失败原因）、
  金额、商户、时间来源标记、去重指纹
- **命中时 MUST 额外记录页面文本摘要**：取页面文本前 3 行、每行截断到 24 字，
  用 ` | ` 连接。误识别的排查全靠它——「为什么聊天页被判成支付结果页」这种问题，
  没有页面摘要就只能靠猜；有摘要能直接看到是哪个词凑出的证据
- 摘要 MUST NOT 包含超过 3 行、MUST NOT 包含完整页面、MUST NOT 包含账号或头像信息；
  单条摘要总长度 MUST 不超过 96 字
- 日志内容 MUST NOT 包含整页文本、账号、头像等与本机账本无关的信息
- 设置页 MUST 能查看最近日志、清空日志；清空 MUST 立即落盘生效

#### Scenario: 日志能区分方向与时间来源
- GIVEN 识别日志开关已开启
- WHEN 完成一次识别
- THEN 该条日志包含方向（收入/支出）与账单时间
- AND 时间来自回退时该条标注「时间回退」

#### Scenario: 命中时留下页面摘要
- GIVEN 识别日志开关已开启
- WHEN 某次识别命中并弹出确认卡片
- THEN 该条日志带一段页面文本摘要（最多 3 行、每行最多 24 字）
- AND 摘要里能看出命中时页面上的关键几行文字

#### Scenario: 重启后还能看到昨天的重复记录
- GIVEN 昨天识别过同一笔 3.50 元，弹了两次确认
- WHEN 用户今天重新打开应用并查看识别日志
- THEN 两条记录仍然在，且能看出它们的指纹是否相同

### Requirement: 金额解析必须排除非交易金额
系统 SHALL 在判断「页面是否只有一个金额」之前，先按**语义优先级**确定本次交易金额，
再对剩余的候选做排除，最后才判定歧义。

MUST 排除的情况：

- 本行或前后两行内出现「余额 / 可用余额 / 账户余额 / 零钱余额」——该数字是账户余额
- 前后两行内出现 `KB/s`、`℃` 等单位——该数字是状态栏读数
- 本行或紧邻行出现 `订单金额 / 商品金额 / 原价 / 优惠 / 立减金 / 已省 / 红包金额` 等标签
  ——这些是原价与优惠，不是本次实付金额
- 本行或紧邻行出现 `标价 / 汇率 / 外币 / 美元 / USD` 等外币信息
  ——微信外币支付页会同时出现「-42.00」（实付人民币）与「6.24美元」（标价）

「余额宝」MUST NOT 被当作余额标签（它是支付方式）。

当页面存在**带方向前缀的金额**（`支出X元` / `收入X元`）时，系统 MUST 以它为准，
MUST NOT 再因为它与其他数字共存而判歧义。

排除之后，若仍存在多个互不相同的金额且没有任何一个具备更高语义优先级，系统 MUST 放弃识别。

**OCR 丢小数点 MUST 被拦住。** 交易金额在微信 / 支付宝上一律显示两位小数，
`¥27.00` 被 OCR 读成 `¥2700` 时会放大 100 倍（真机出现过：聊天里 27 元的转账提示被读成 2700）。
因此：**金额若只有整数、没有小数点，且该页面属于支付结果页（没有交易单号、没有账单时间）时，
系统 MUST 判为「小数点可能丢失」并放弃本次识别**，MUST NOT 弹窗，
日志 MUST 记为「金额疑似丢失小数点」。

同一页面上若同时存在「带货币符号的整数金额」与「带两位小数的金额」，
系统 MUST 优先采用带两位小数的那个。

> 依据：真机实测支付宝「扫经营码付款」详情页同时出现 `订单金额 17500.00`、
> `某银行立减金 -0.22` 与 `支出17499.78元`，旧逻辑判「金额歧义」永不记账。

#### Scenario: 订单金额与优惠不参与歧义判断
- GIVEN 支付宝详情页同时出现 `订单金额 17500.00`、`某银行立减金 -0.22` 与 `支出17499.78元`
- WHEN 解析金额
- THEN 只有 `支出17499.78元` 被认定为交易金额
- AND 金额为 1749978 分
- AND 方向为支出

#### Scenario: 余额与状态栏数字不参与歧义判断
- GIVEN 支付宝账单页同时出现 `-25.00`（交易金额）、`¥217.01`（余额，上一行是「余额」）与 `5.24`（状态栏网速，相邻行有 `KB/s`）
- WHEN 解析金额
- THEN 只有 `-25.00` 被认定为交易金额
- AND 金额为 2500 分

#### Scenario: 余额宝不被当成余额
- GIVEN 付款成功页含「支付方式 余额宝」与金额 `¥25.50`
- WHEN 解析金额
- THEN `¥25.50` 仍被认定为交易金额

#### Scenario: 外币标价不参与歧义判断
- GIVEN 微信外币支付详情页同时出现 `-42.00`（实付）、`标价 6.24美元`、`汇率 1美元=6.72631人民币`
- WHEN 解析金额
- THEN 只有 `-42.00` 被认定为交易金额
- AND 金额为 4200 分

#### Scenario: 小数点丢失时放弃识别
- GIVEN 支付结果页上的金额被 OCR 读成 `¥2700`（原文是 `¥27.00`），页面没有账单时间与交易单号
- WHEN 解析金额
- THEN 放弃识别，不弹出确认悬浮窗
- AND 日志记为「金额疑似丢失小数点」
- AND 不会记成一笔 2700 元的支出

#### Scenario: 同时有带小数的金额时优先它
- GIVEN 同一页面上既有 `¥2700`（OCR 丢小数点）又有 `¥27.00`
- WHEN 解析金额
- THEN 采用 `¥27.00`（2700 分）

#### Scenario: 排除后仍歧义则放弃
- GIVEN 页面存在两个互不相同、且都没有方向前缀的金额，也没有任何可排除的上下文
- WHEN 解析金额
- THEN 判为金额歧义并放弃识别
- AND 不弹出确认悬浮窗
