# 变更：让自动记账在 HyperOS 上可靠常驻

## 动机

自动记账依赖无障碍服务。在Android 16 真机（Android 16 / HyperOS）上实测出现：

- 进程仍在，`dumpsys` 显示无障碍服务**已绑定**；
- 但**事件不再送达**，用户点开微信账单页什么都不弹；
- 用户重新开关一次无障碍服务即恢复。

用户已配置：自启动允许、省电策略「无限制」、电池白名单、`standby bucket = active`，问题仍会复现。
结果是自动记账在最需要它的时候（长时间未操作手机后付款）恰好失效，而且**失效是静默的**——用户以为它在工作。

## 范围

在范围内：

- 先诊断，确认「进程被冻结」这一根因假设，并给出可复现的观测方法
- 对比「前台服务 + 常驻通知」「AlarmManager 心跳自查」「JobScheduler/WorkManager」三类做法的实际效果与代价
- 落地被选中的组合：提高进程优先级、让失效**可被发现**、让用户能自行恢复
- 设置页展示服务的真实运行状态（最近一次事件时间、疑似冻结提示）
- Android 16 真机 真机验收：解放手 5–10 分钟后仍能收到微信无障碍事件

不在范围内：

- 申请 `INTERNET` 或任何网络能力（硬性红线）
- 引入 Shizuku / ADB 提权写 `Settings.Secure` 自动重开无障碍（需额外依赖与用户操作）
- 双进程守护、JobScheduler 拉活等 Android 8+ 已不可行或违规的做法
- 常驻 `PARTIAL_WAKE_LOCK`（耗电不可接受）
- 修改微信/支付宝本身，或使用 root
- 真实支付一笔（验收一律用 debug 模拟页与微信历史账单详情页）

## 方法

先做真机诊断：在已知冻结窗口内抓取进程状态与事件时间戳，确认是「进程被冻结」而不是「服务被解绑」或「授权丢失」。
随后按对比结论实现「前台服务（带常驻通知）+ 事件心跳 + 状态展示」的组合：前台服务负责把进程从 cached 区间抬出来，心跳负责在事件断流时把问题暴露给用户，状态展示负责让用户看见而不是猜。

## 待确认

- 是否接受常驻通知（需要新增 `POST_NOTIFICATIONS` 权限；这是本变更唯一的用户可见代价）
- 失效时的恢复路径：仅「提示用户重新开关」还是「提供一键跳转无障碍设置」

---

## 实施后的结论（原假设被推翻）

实施与实测之后，本变更的**原始假设是错的**，需要在这里如实更正：

**原假设**：HyperOS 会冻结进程，导致绑定还在但事件不来。

**实测结论**：进程从不被冻结；服务失效的路径是
「应用被 force-stop → Android 把无障碍权限从安全设置里移除」，这是 AOSP 写死的
平台行为。而本应用还有**第二个自己的 bug**：`onServiceConnected` 里同步
`warmUp()` 悬浮窗，阻塞服务连接直到系统 `wait for adding window timeout` 放弃绑定。
后者已修复，是「开关开着却显示未开启」的真正原因。

因此本变更实际交付的是：

- 前台服务 + 常驻通知（降低被系统清理的概率）
- **修掉服务连接阻塞**（真正解决了「开了却不生效」）
- 失效可被发现：实时监听 + 告警通知 + 设置页区分「从没设置/被撤销」
- 电池优化豁免、自启动引导、任务锁定引导
- 可选：Shizuku 15 分钟巡检自动写回（与 Tally 同款；没装不影响其它功能）

**明确做不到**：被 force-stop 之后，纯应用层无法恢复权限，必须重新授权一次。
这一条已写进 README 的边界说明。
