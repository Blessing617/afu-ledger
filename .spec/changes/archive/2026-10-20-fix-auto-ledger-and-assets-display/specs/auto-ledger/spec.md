# Delta：auto-ledger

## MODIFIED Requirements

### Requirement: 去重
系统 SHALL 对同一笔账单只请求一次确认；重复的页面事件或服务重复回调 MUST NOT
产生第二次确认或第二笔交易。

去重 MUST 有两层，且第二层必须能跨页面生效：

1. **指纹层**（长期）：由 [交易单号指纹与持久化去重] 定义，用于「忽略过 / 入账过」的账单在有效期内不再打扰。
2. **会话层**（短窗口）：同一来源包内，**金额相同、方向相同**的命中在
   `SESSION_WINDOW`（默认 120 秒）内视为同一笔，即使两次命中的指纹不同。
   这层存在的唯一理由：同一笔付款在支付宝里会依次出现两个页面
   （「聚合收款 / 付款成功」与「支付成功」），两页的商户与单号字段并不一致。

会话层的**例外**：两次命中都解析出非空、且互不相同的交易单号时，MUST 视为两笔不同交易。
只要有一方单号为空，就 MUST 按会话层合并。

去重指纹 MUST NOT 包含**由页面文本猜出来的商户名**：真机实测同一张账单两次 OCR
会把商户名读成 `阿佑鲜烫牛內米线` 与 `阿佑鮮烫牛内米线`（简繁/形近字差异），
带进指纹就变成两个指纹，同一张账单反复弹窗。商户名只用于展示。

代价是「同一分钟内给两家不同商户付了相同金额」会被合并成一次确认 —— 该场景罕见，
且用户仍可手动补记。

#### Scenario: 页面反复刷新不重复弹出
- GIVEN 用户停留在账单详情页，页面事件被多次触发
- WHEN 同一笔账单在同一时间窗内被再次识别
- THEN 不出现第二个悬浮窗
- AND 最多只产生一笔交易

#### Scenario: 商户名读错不影响去重
- GIVEN 同一张账单第一次识别出商户「阿佑鲜烫牛內米线」，第二次识别出「阿佑鮮烫牛内米线」
- WHEN 两次识别完成
- THEN 两次得到同一个指纹
- AND 只弹一次确认

#### Scenario: 同金额不同分钟视为两笔
- GIVEN 同一商户先后有两笔 17.00 元，账单时间分别为 17:59 与 18:01
- WHEN 两次识别完成
- THEN 各自弹出一次确认，互不去重

#### Scenario: 支付宝一笔付款跨两个页面只记一次
- GIVEN 用户完成一笔 20.00 元支付宝付款
- AND 先停在「付款成功（聚合收款）」页：该页有交易单号，但商户字段缺失
- AND 随后停在「支付成功」页：该页无交易单号，但有商户名
- WHEN 两个页面先后被识别（间隔在会话窗口内）
- THEN 只出现一次确认
- AND 只产生一笔 20.00 元支出
- AND 该笔的备注是商户名，而不是「未识别到商户」

#### Scenario: 两个页面都缺单号也只记一次
- GIVEN 同一笔付款的两个页面都不渲染交易单号
- WHEN 两次识别先后完成
- THEN 两次命中落在同一会话层
- AND 只产生一笔交易

#### Scenario: 两个页面单号不同视为两笔
- GIVEN 两次命中都解析出非空且互不相同的交易单号
- WHEN 第二次识别完成
- THEN 系统按两笔处理，各自弹一次确认

#### Scenario: 同额同向的两笔真实消费不被误合并
- GIVEN 用户在 60 秒内先后买了两瓶水，各 2.00 元，两笔都有各自的交易单号
- WHEN 两次识别完成
- THEN 两次都弹确认（因为两个单号都非空且不同）

### Requirement: 交易单号指纹与持久化去重
系统 SHALL 以「交易单号」作为同一笔账单的**长期**主指纹，并持久化「已提示」与「已忽略」两种状态。

**短窗口内的同一笔判定 MUST 由 [去重] 的会话层负责**，指纹层不再承担「挡住紧接着的第二次命中」的职责：
单号缺失或两页单号不一致（一有一无）是支付宝的常态，只靠指纹会漏掉跨页重复。

**系统 MUST NOT 通过模拟点击（如展开「更多」）来获取交易单号**：账本应用不得操作用户的其他应用界面。

无交易单号时，指纹 MUST 退化为「包名 + 金额 + 方向 + 商户名 + 账单时间」。
其中账单时间 MUST 使用解析出的账单时间而不是识别时刻 —— 支付宝的**旧版**账单详情布局
不渲染交易单号（25 张样本里有 21 张属于旧版），退化指纹是这个场景下的常态，
用它才能区分同商户同金额的不同笔。

单号字段的标签集 MUST 至少包含：`交易单号`、`商户单号`、`商家订单号`、`订单号`、**`转账单号`**。
微信的转账类账单用的正是「转账单号」，漏掉它会让转账类账单全部退化。

用户主动忽略或确认过的指纹 MUST 在 7 天内不再触发确认；指纹记录 MUST 仅存于本机。

#### Scenario: 支付宝无单号时按账单时间退化去重
- GIVEN 支付宝账单页不提供交易单号，账单时间为 2026-10-19 18:01:22，金额 2500 分，商户「森众餐饮」
- WHEN 用户忽略后再 10 秒重新打开同一张账单
- THEN 不出现确认悬浮窗

#### Scenario: 同商户同金额不同分钟视为两笔
- GIVEN 同一商户先后有两笔 17.00 元，账单时间分别为 17:59:40 与 18:01:22
- WHEN 两次识别完成
- THEN 各自弹出一次确认，互不去重

#### Scenario: 确认过的账单不重复入账
- GIVEN 用户对交易单号为 B 的账单点过「记一笔」
- WHEN 用户再次打开该账单
- THEN 不出现确认悬浮窗

#### Scenario: 不模拟点击对方界面
- GIVEN 支付宝账单页的交易单号需要展开「更多」才可见
- WHEN 识别流程执行
- THEN 系统不对支付宝界面执行任何点击操作
- AND 按退化指纹去重

### Requirement: 自动记账设置
系统 SHALL 在设置页提供自动记账区块，包含总开关、截图 OCR 开关、默认账户、默认分类与识别日志开关，并持久保存。

区块 MUST 采用**先开关、后展开**的结构：

- 总开关关闭时，区块只显示总开关本身（可带一行摘要），MUST NOT 常驻铺开无障碍状态、默认账户、默认分类、OCR 状态与识别日志
- 总开关打开时，其余设置 MUST 以**展开动画**（纵向高度与透明度过渡，时长 150–300ms）呈现，MUST NOT 突然整块跳出
- 用户关闭总开关时，详情 MUST 同样以动画收起，且已保存的默认账户 / 默认分类 MUST NOT 被清空

设置页 MUST 显示截屏 OCR 的运行状态：能力是否可用、最近一次 OCR 的耗时或失败原因；该状态 MUST NOT 伪造「正常」。

#### Scenario: 关闭截图 OCR 后微信不再识别
- GIVEN 用户关闭了截图 OCR 开关
- WHEN 用户停留在微信支付成功页
- THEN 不调用截图能力
- AND 不出现确认悬浮窗
- AND 支付宝的识别不受影响

#### Scenario: 显示 OCR 运行状态
- GIVEN 用户进入设置页的自动记账区块，且总开关已开启
- WHEN 查看截图 OCR 一项
- THEN 显示当前是否可用
- AND 开启后显示最近一次 OCR 的结果（成功耗时或失败原因）

#### Scenario: 修改默认账户
- GIVEN 用户把默认账户改为「招行卡」
- WHEN 下一次悬浮窗展示
- THEN 账户预选为「招行卡」

#### Scenario: 默认分类失效时回退
- GIVEN 用户设置的默认分类已被删除
- WHEN 悬浮窗展示
- THEN 分类回退为支出分类「其他」

#### Scenario: 识别日志可查
- GIVEN 用户开启了识别日志
- WHEN 识别成功或失败发生
- THEN 设置页可查看最近若干条识别结果与失败原因
- AND 日志仅保存在本机

#### Scenario: 总开关关闭时只显示开关
- GIVEN 自动记账总开关处于关闭状态
- WHEN 用户进入设置页的自动记账区块
- THEN 只看到总开关（与一行摘要）
- AND 看不到默认账户、默认分类、OCR 与识别日志等条目

#### Scenario: 打开总开关后展开详情
- GIVEN 自动记账区块处于收起状态
- WHEN 用户打开总开关
- THEN 无障碍状态、默认账户、默认分类、截图 OCR 与识别日志依次向下展开
- AND 展开过程是平滑的纵向过渡，不是瞬间出现

#### Scenario: 收起不清空配置
- GIVEN 用户此前设过默认账户与默认分类
- WHEN 用户关闭总开关再重新打开
- THEN 详情展开后默认账户与默认分类仍是之前的选择

## ADDED Requirements

### Requirement: 商户名（备注）提取
系统 SHALL 从账单页提取**商户实体名**作为确认卡片的商户展示与入账备注。

候选来源与优先级：

1. 商户字段标签的值：`收款方全称`、`商户全称`、`收款方`、`商户名称`、`商家名称`、`对方账户`、`商户简称`
2. 金额所在视觉行的邻近行中，**单个 cell** 级别的文本（MUST NOT 直接使用整行拼接结果）
3. 取不到时返回「无商户」，MUST NOT 编造或使用占位文案

系统 MUST 排除下列文本，即使它们出现在金额邻近行：

- 操作/按钮类文案及其描述：`返回`、`按钮`、`回首页`、`返回商家`、`完成`、`确定`、`忽略`、`参与`、`去参与`、`一键领`、`查看详情`、`联系商家` 等
- 页面活动/广告文案：`支付有礼`、`红包`、`体验金`、`账单贴纸`、`碰友节`、`去参与` 等
- 多个按钮被拼进同一行的文本（含「按钮」「回首页」「返回商家」等片段的整行）

商户名仍 MUST NOT 参与去重指纹。

备注落库规则：商户名存在时写入备注；取不到时备注 MUST 为空字符串，MUST NOT 写入「未识别到商户」「无」这类占位文字。

#### Scenario: 支付成功页取到真实商户
- GIVEN 支付宝支付成功页含「杭州深度求索」「支付成功」「¥20.00」「完成」
- WHEN 提取商户名
- THEN 商户为「杭州深度求索」
- AND 备注为「杭州深度求索」

#### Scenario: 按钮文案不当商户
- GIVEN 页面金额邻近行是「回首页 返回商家」与「返回 按钮」
- WHEN 提取商户名
- THEN 这些文本都不被当作商户
- AND 若没有其它可用的商户字段，商户为「无商户」

#### Scenario: 取不到商户时备注为空
- GIVEN 页面没有任何可用的商户实体名
- WHEN 用户确认入账
- THEN 该笔交易的备注为空字符串
- AND 备注里不出现「未识别到商户」之类的占位文字

### Requirement: 授权状态实时可见
系统 MUST 让设置页的自动记账区块及时反映无障碍授权的真实状态，MUST NOT 出现「其实已经开启了还显示未开启」的长期滞后。

实现 MUST 满足：

- 监听 `AccessibilityManager` 的全局状态变化与（API 33+）服务级状态变化，收到变化后立即重算并刷新界面
- 应用回到前台（`ON_RESUME`）时立即重算
- 在「未开启」状态且用户刚从授权页返回时，MUST 以短间隔（≤1 秒）复检若干次（覆盖系统启用列表的延迟），一旦检到已开启立即转为已开启，无需用户手动切页
- 状态刷新 MUST NOT 以伪造方式呈现：检不到就继续显示未开启，不得先乐观显示为已开启

#### Scenario: 从系统设置开启后回到应用立即变绿
- GIVEN 设置页显示「无障碍服务未开启」
- WHEN 用户跳转系统无障碍设置开启本服务并返回应用
- THEN 2 秒内该行变为「无障碍服务已开启」
- AND 不需要用户切走再回来

#### Scenario: 授权被撤销时立即提示
- GIVEN 服务此前已开启，设置页显示已开启
- WHEN 系统撤销了本应用的无障碍授权（应用处于前台设置页）
- THEN 该行在 2 秒内变为未开启并给出原因说明

#### Scenario: 检不到时如实显示
- GIVEN 用户并未开启无障碍服务
- WHEN 用户在设置页停留
- THEN 状态一直是「未开启」
- AND 不会先显示已开启再退回
