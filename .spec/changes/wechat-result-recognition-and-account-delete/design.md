# 设计方案

## 识别：为什么只调顺序，不动判据

当前 `PaymentPageDetector.detect` 的顺序是：

```
强排除 → 列表页 → 主界面 → 账单页正向准入 → 结果页判定 → 金额
```

微信支付成功页（`支付成功 / 商户 / ¥98.00 / 原价 / 优惠 / 完成`）凑不出任何 `billStrongFields`，
在「账单页正向准入」就被 `NOT_PAYMENT_PAGE` 拦掉，结果页判定根本没跑。

改动：把结果页判定提到正向准入之前，结果页成立就直接继续解析金额；不成立才走原来的准入。

```
强排除 → 列表页 → 主界面 → 结果页判定 →（否则）账单页正向准入 → 金额
```

不动判据的理由：

- 结果页判据本身就要求「无账单标题 / 无交易单号 / 无账单时间字段」，这三个条件让真实账单页
  （支付宝旧版一定带「支付时间」）不会被误判成结果页；
- 误触发防线仍然是主界面 / 列表页排除，它们在结果页判定之前执行，支付宝首页的历史通知
  「森众餐饮 付款成功 ¥25.00」依旧被拦住（负样本 fixture 覆盖）；
- 不用「页面出现成功词就放行」这种放宽，避免把支付过程中的「确认付款」「待支付」页面也放进来。

金额侧不改：`AmountParser` 的价格标签（原价 / 优惠 / 立减 / 已省）排除规则已经覆盖微信
支付成功页的形态 —— 标签与数值同行、或标签在值的上一行，两种 OCR 切行都能排掉。
新增的 fixture 只是把这个场景钉进回归。

## 账户删除：复用外键级联，不做软删除

`transactions.accountId` 外键已是 `onDelete = CASCADE`，`AccountRepository.delete` 也已存在，
所以删除 = 一条 `DELETE FROM accounts WHERE id = ?`，交易由 SQLite 级联清理，不开事务也不用手写 IN 列表。

确认弹窗需要交易笔数：给 `TransactionDao` 加 `COUNT(*) WHERE accountId = :id`。

不做软删除 / 回收站的理由：本变更是为了清理误建的空账户；软删除要多一套「回收站」UI、
过滤与清理策略，收益与复杂度不成比例。删除前的二次确认与笔数提示是更划算的保护。

## 归档：为什么移除而不是保留

评估结论：**移除**。

- 归档的真实用途是「留着历史交易但不想再看到这个账户」。本项目是单人自用账本，账户数量个位数，
  这个需求可以用「直接不记账在该账户」覆盖；
- 它带来的复杂度却是实打实的：资产页一个额外分组、总资产口径两套、排序的特例分支、
  编辑对话框两个语义相近的按钮、备份格式一个字段、spec 里七处「未归档」措辞；
- 用户唯一一次真正用到它的场景是「误建账户删不掉」——正是删除要解决的问题。

数据上保留 `archived` 列（不删列），避免备份与 schema 的大改；迁移 `3 → 4` 只做
`UPDATE accounts SET archived = 0`，界面不再读写这个字段。

## 迁移与兼容

- `AFU_DB_SCHEMA_VERSION` 3 → 4，手写 `Migration(3, 4)`（`AutoMigration` 处理不了数据修正）；
- 备份 JSON 里的 `archived` 字段：导出不再写入；导入时 `ignoreUnknownKeys` 已开，
  旧文件里的该字段会被忽略，导入后账户一律为普通账户；
- `AccountWithBalance.archived` / 领域模型字段保留，仅 UI 不再使用，降低改动面。

## 默认账户与定时规则的降级

- `PaymentConfirmController` 已有「默认账户不存在则回退 `accounts.first()`」的逻辑，无需改动，
  补一条单测钉住；
- `RunDueSchedulesUseCase` 已有「账户不存在 → 暂停规则」的逻辑（`pausedReason`），
  删除账户会自然触发；只需要补测试确认它确实暂停而不是崩溃。
