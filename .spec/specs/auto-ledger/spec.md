# auto-ledger

## Purpose

在用户完成付款后，从支付结果页读取金额并请求确认，确认后自动入账，避免手动记账的遗漏与重复劳动；识别与入账全程离线，不申请网络权限。

## Requirements

### Requirement: 无障碍服务与授权引导
系统 SHALL 提供一个可在设置中开关的无障碍服务，用于读取受支持应用的账单详情页，并在其无障碍文本不可用时截取屏幕交给本机离线 OCR；未授权时系统 MUST 明确展示未开启状态，而不是静默失效。

服务声明 MUST 显式包含截屏能力，且服务的授权说明 MUST 让用户知道「会截取屏幕画面并在本机做文字识别」。

服务 MUST NOT 声明 `FLAG_REQUEST_ACCESSIBILITY_BUTTON`（见「无感化」Requirement）。

#### Scenario: 总开关关闭时不识别
- GIVEN 自动记账总开关处于关闭状态
- WHEN 用户在支付宝打开一张账单详情页
- THEN 不出现任何确认悬浮窗
- AND 不产生交易

#### Scenario: 总开关关闭时不截图
- GIVEN 自动记账总开关处于关闭状态
- WHEN 用户停留在微信账单页并产生页面事件
- THEN 不调用截图能力
- AND 不出现任何确认悬浮窗

#### Scenario: 授权说明披露截屏行为
- GIVEN 用户查看系统的无障碍服务详情页
- WHEN 阅读本服务的授权说明
- THEN 说明中包含「截取屏幕画面用于本机文字识别」的表述

#### Scenario: 首次进入引导授权
- GIVEN 用户从未开启过本应用的无障碍服务
- WHEN 用户进入设置页的「自动记账」区块
- THEN 显示无障碍服务未开启的状态
- AND 提供跳转系统无障碍设置的入口
- AND 提示 HyperOS 上还需允许「受限制的设置」并关闭省电限制

#### Scenario: 授权后恢复识别
- GIVEN 用户已按引导开启无障碍服务
- WHEN 用户打开一张支付宝账单详情页
- THEN 正常出现确认悬浮窗

### Requirement: 确认悬浮窗
系统 SHALL 在识别成功后于当前页面之上展示确认卡片，包含金额、商户名（若有）、账户与分类选择，以及「记一笔」与「忽略」操作；用户确认前 MUST NOT 写入任何交易。

#### Scenario: 确认后入账
- GIVEN 悬浮窗展示金额 25.50、默认账户「现金」、默认分类「餐饮」
- WHEN 用户点击「记一笔」
- THEN 新增一笔 2550 分的支出交易
- AND 该交易的账户为「现金」、分类为「餐饮」、备注为识别到的商户名

#### Scenario: 当场修改分类
- GIVEN 悬浮窗已展示默认分类「餐饮」
- WHEN 用户改为「交通」并点击「记一笔」
- THEN 入账交易的分类为「交通」

#### Scenario: 忽略或超时丢弃
- GIVEN 悬浮窗已展示
- WHEN 用户点击「忽略」，或悬浮窗在 60 秒内未被操作
- THEN 悬浮窗消失
- AND 不产生任何交易

#### Scenario: 无可用账户时引导创建
- GIVEN 系统中没有任何未归档的资产账户
- WHEN 识别成功需要展示悬浮窗
- THEN 提示先创建资产账户，并提供跳转入口
- AND 不产生交易

### Requirement: 去重
系统 SHALL 对同一笔账单只请求一次确认；重复的页面事件或服务重复回调 MUST NOT
产生第二次确认或第二笔交易。

去重 MUST 有两层，且第二层必须能跨页面生效：

1. **指纹层**（长期）：由 [交易单号指纹与持久化去重] 定义，用于「忽略过 / 入账过」的账单在有效期内不再打扰。
2. **会话层**（短窗口）：同一来源包内，**金额相同、方向相同**的命中在
   `SESSION_WINDOW`（默认 120 秒）内视为同一笔，即使两次命中的指纹不同。
   这层存在的唯一理由：同一笔付款在支付宝里会依次出现两个页面
   （「聚合收款 / 付款成功」与「支付成功」），两页的商户与单号字段并不一致。

会话层的**例外**：两次命中都解析出非空、且互不相同的交易单号时，MUST 视为两笔不同交易。
只要有一方单号为空，就 MUST 按会话层合并。

去重指纹 MUST NOT 包含**由页面文本猜出来的商户名**：真机实测同一张账单两次 OCR
会把商户名读成 `阿佑鲜烫牛內米线` 与 `阿佑鮮烫牛内米线`（简繁/形近字差异），
带进指纹就变成两个指纹，同一张账单反复弹窗。商户名只用于展示。

代价是「同一分钟内给两家不同商户付了相同金额」会被合并成一次确认 —— 该场景罕见，
且用户仍可手动补记。

#### Scenario: 页面反复刷新不重复弹出
- GIVEN 用户停留在账单详情页，页面事件被多次触发
- WHEN 同一笔账单在同一时间窗内被再次识别
- THEN 不出现第二个悬浮窗
- AND 最多只产生一笔交易

#### Scenario: 商户名读错不影响去重
- GIVEN 同一张账单第一次识别出商户「阿佑鲜烫牛內米线」，第二次识别出「阿佑鮮烫牛内米线」
- WHEN 两次识别完成
- THEN 两次得到同一个指纹
- AND 只弹一次确认

#### Scenario: 同金额不同分钟视为两笔
- GIVEN 同一商户先后有两笔 17.00 元，账单时间分别为 17:59 与 18:01
- WHEN 两次识别完成
- THEN 各自弹出一次确认，互不去重

#### Scenario: 支付宝一笔付款跨两个页面只记一次
- GIVEN 用户完成一笔 20.00 元支付宝付款
- AND 先停在「付款成功（聚合收款）」页：该页有交易单号，但商户字段缺失
- AND 随后停在「支付成功」页：该页无交易单号，但有商户名
- WHEN 两个页面先后被识别（间隔在会话窗口内）
- THEN 只出现一次确认
- AND 只产生一笔 20.00 元支出
- AND 该笔的备注是商户名，而不是「未识别到商户」

#### Scenario: 两个页面都缺单号也只记一次
- GIVEN 同一笔付款的两个页面都不渲染交易单号
- WHEN 两次识别先后完成
- THEN 两次命中落在同一会话层
- AND 只产生一笔交易

#### Scenario: 两个页面单号不同视为两笔
- GIVEN 两次命中都解析出非空且互不相同的交易单号
- WHEN 第二次识别完成
- THEN 系统按两笔处理，各自弹一次确认

#### Scenario: 同额同向的两笔真实消费不被误合并
- GIVEN 用户在 60 秒内先后买了两瓶水，各 2.00 元，两笔都有各自的交易单号
- WHEN 两次识别完成
- THEN 两次都弹确认（因为两个单号都非空且不同）

### Requirement: 自动记账设置
系统 SHALL 在设置页提供自动记账区块，包含总开关、截图 OCR 开关、默认账户、默认分类与识别日志开关，并持久保存。

区块 MUST 采用**先开关、后展开**的结构：

- 总开关关闭时，区块只显示总开关本身（可带一行摘要），MUST NOT 常驻铺开无障碍状态、默认账户、默认分类、OCR 状态与识别日志
- 总开关打开时，其余设置 MUST 以**展开动画**（纵向高度与透明度过渡，时长 150–300ms）呈现，MUST NOT 突然整块跳出
- 用户关闭总开关时，详情 MUST 同样以动画收起，且已保存的默认账户 / 默认分类 MUST NOT 被清空

设置页 MUST 显示截屏 OCR 的运行状态：能力是否可用、最近一次 OCR 的耗时或失败原因；该状态 MUST NOT 伪造「正常」。

#### Scenario: 关闭截图 OCR 后微信不再识别
- GIVEN 用户关闭了截图 OCR 开关
- WHEN 用户停留在微信支付成功页
- THEN 不调用截图能力
- AND 不出现确认悬浮窗
- AND 支付宝的识别不受影响

#### Scenario: 显示 OCR 运行状态
- GIVEN 用户进入设置页的自动记账区块，且总开关已开启
- WHEN 查看截图 OCR 一项
- THEN 显示当前是否可用
- AND 开启后显示最近一次 OCR 的结果（成功耗时或失败原因）

#### Scenario: 修改默认账户
- GIVEN 用户把默认账户改为「招行卡」
- WHEN 下一次悬浮窗展示
- THEN 账户预选为「招行卡」

#### Scenario: 默认分类失效时回退
- GIVEN 用户设置的默认分类已被删除
- WHEN 悬浮窗展示
- THEN 分类回退为支出分类「其他」

#### Scenario: 识别日志可查
- GIVEN 用户开启了识别日志
- WHEN 识别成功或失败发生
- THEN 设置页可查看最近若干条识别结果与失败原因
- AND 日志仅保存在本机

#### Scenario: 总开关关闭时只显示开关
- GIVEN 自动记账总开关处于关闭状态
- WHEN 用户进入设置页的自动记账区块
- THEN 只看到总开关（与一行摘要）
- AND 看不到默认账户、默认分类、OCR 与识别日志等条目

#### Scenario: 打开总开关后展开详情
- GIVEN 自动记账区块处于收起状态
- WHEN 用户打开总开关
- THEN 无障碍状态、默认账户、默认分类、截图 OCR 与识别日志依次向下展开
- AND 展开过程是平滑的纵向过渡，不是瞬间出现

#### Scenario: 收起不清空配置
- GIVEN 用户此前设过默认账户与默认分类
- WHEN 用户关闭总开关再重新打开
- THEN 详情展开后默认账户与默认分类仍是之前的选择

### Requirement: 不联网与本地隐私
系统 MUST NOT 申请 `INTERNET` 权限；自动记账的识别与入账 MUST 全部在本机完成，OCR 模型 MUST 随 APK 一同分发而不是运行时下载。

截图与 OCR 中间产物 MUST 只存在于内存中：MUST NOT 写入文件、相册、日志或数据库；识别结束后 MUST 立即释放。开启识别日志时也只允许保留截断后的文本摘要，不得保留完整画面或整页文本。

#### Scenario: 合并后的 Manifest 无网络权限
- GIVEN 构建 debug 与 release APK
- WHEN 检查合并后的 AndroidManifest.xml
- THEN 不包含 `android.permission.INTERNET`
- AND 不包含 `android.permission.SYSTEM_ALERT_WINDOW`
- AND 不包含 `android.permission.READ_SMS`
- AND 不包含 `android.permission.READ_MEDIA_IMAGES`

#### Scenario: OCR 模型内置在 APK 内
- GIVEN 构建 release APK
- WHEN 检查 APK 内容
- THEN 其中包含 OCR 模型文件
- AND 应用启动与识别过程都不发生任何网络请求

#### Scenario: 截图不落盘
- GIVEN 完成一次微信截图 OCR 识别
- WHEN 检查应用私有目录、相册与数据库
- THEN 找不到任何截图文件或位图数据
- AND 数据库中没有该页面的整页文本

#### Scenario: 不保存原始页面文本
- GIVEN 识别日志处于关闭状态
- WHEN 完成一次识别
- THEN 数据库与 DataStore 中不保留该页面的原始文本快照
- AND 仅保留交易本身与去重所需的最小指纹

### Requirement: 小米 14 Pro / Android 16 适配
系统 SHALL 在小米 14 Pro（Android 16 / HyperOS）上端到端可用：受限设置可解除、服务能保持运行、悬浮窗能正常显示、微信可通过截图 OCR 完成识别，且截图频次受节流约束不会持续占用资源。

#### Scenario: 受限设置引导
- GIVEN 用户在 HyperOS 上开启无障碍服务时遇到「受限制的设置」拦截
- WHEN 用户查看自动记账的授权引导
- THEN 引导中给出「应用信息 → 允许受限制的设置」的具体路径

#### Scenario: 真机端到端
- GIVEN 小米 14 Pro 已按引导完成授权
- WHEN 用户完成一笔支付宝支付并停留在结果页
- THEN 出现确认悬浮窗
- AND 确认后首页出现对应交易，账户余额正确变化

#### Scenario: 真机微信 OCR 端到端
- GIVEN 小米 14 Pro 已按引导完成授权，截图 OCR 开关开启
- WHEN 用户打开微信历史账单详情页并停留
- THEN 出现确认悬浮窗，金额与页面显示一致
- AND 点「忽略」后不产生交易

#### Scenario: 持续停留不产生截图风暴
- GIVEN 用户在微信内正常浏览，页面持续产生无障碍事件
- WHEN 在该应用内持续操作若干分钟
- THEN 截图次数与页面停留时长之间保持受控比例（不超过节流上限）
- AND 应用不出现可感知的卡顿或明显耗电

### Requirement: 截图 OCR 文本采集通道
系统 SHALL 在受支持应用的页面不暴露无障碍文本节点时，通过无障碍服务的 `AccessibilityService.takeScreenshot()` 截取当前屏幕，并用**打包在 APK 内的离线 OCR 模型**将其转换为文本行列表，产出与无障碍采集同形态的页面文本快照供后续识别使用。

OCR MUST 在本机完成，MUST NOT 依赖网络、远程服务或运行时下载的模型文件。

OCR 执行 MUST NOT 发生在无障碍事件回调所在线程；识别期间 MUST NOT 阻塞或拖慢当前页面交互。

**耗时约束**：单次「截图 → 出文本行」在小米 14 Pro 上、针对**真实账单页（30 行左右文本）**的处理耗时 MUST ≤ 400ms（不含事件去抖与节流等待）。

OCR MUST 采用**整页一次推理**的方案，MUST NOT 使用「先检测文本框、再逐行识别」的两阶段方案。

> 依据：两阶段方案的成本与「所有行的宽度之和」成正比（实测约 0.14ms/宽度单位），
> 30 行就要做 1 次检测 + 30 次识别，实测 1450–2204ms；同样页面改为整页一次推理后
> 降到 283–399ms。且批量推理不能解决这个问题 —— 成本由宽度总和决定，与批次数无关。

截图帧 MUST 在截图完成后尽快交给识别，MUST NOT 因为「等页面完全静止」而反复丢弃已截图帧。

OCR 的输入 MUST 直接使用系统截取的位图，MUST NOT 为了预处理而先转成整屏的 `IntArray` 再转回位图。

#### Scenario: 单次 OCR 处理耗时有上限
- GIVEN 截图 OCR 已初始化完成，用户停留在微信账单详情页（30 行左右文本）
- WHEN 触发一次识别
- THEN 从截图开始到产出文本行的处理耗时 ≤ 400ms
- AND 该耗时被写入设置页的 OCR 状态

#### Scenario: 微信支付成功页由 OCR 命中
- GIVEN 总开关与截图 OCR 开关均已开启，无障碍服务已授权
- WHEN 用户停留在微信「支付成功」页面，该页面的无障碍文本节点为空
- THEN 截取当前屏幕并识别出文本
- AND 产出正确的金额
- AND 出现确认悬浮窗

#### Scenario: 无障碍文本可读时不截图
- GIVEN 用户停留在支付宝「付款成功」结果页，该页面无障碍文本可读且内容完整
- WHEN 识别流程执行
- THEN 直接使用无障碍文本完成识别
- AND 不调用截图能力

### Requirement: 截图触发节流与耗电控制
系统 SHALL 仅在**全部**满足下列条件时截图：自动记账总开关开启、截图 OCR 开关开启、无待确认的悬浮窗正在显示、前台应用属于截图的受支持范围、屏幕点亮且未处于锁屏、距离上一次截图不少于该事件类型对应的最小间隔（窗口状态变化事件使用较短间隔，内容变化事件使用较长间隔）、且页面事件已停止变化到达稳定判定时长。

系统 MUST 对连续未命中做退避：一段时间内多次 OCR 均未命中时，最小间隔 MUST 增长；当前台应用切换或发生窗口状态变化时 MUST 重置退避。

系统 SHALL 把「用户主动操作」（点击）与「页面标识变化」视为**换页**，并按较短的切页间隔放行；该换页信号 MUST 保留到判定真正执行的那一刻，MUST NOT 因为随后到达的内容变化事件而丢失。这条是必需的，因为微信在同一个 Activity 内翻页时只发内容变化事件、不发窗口状态变化事件，仅凭事件类型无法区分「换页」与「同页滚动」。

**首次放行 MUST 不受退避影响**：当用户主动点击（明确意图）时，即使当前处于退避期，也 MUST 按切页间隔放行一次，否则用户翻到支付页时会被历史退避直接拦掉。

**页面稳定判定 MUST 有上限**：页面持续产生轻微变化时，去抖 MUST 仍有最大等待时间，MUST NOT 无限推迟识别。

#### Scenario: 页面事件密集时只截一次
- GIVEN 用户停留在微信支付成功页，页面在 3 秒内触发了十余次内容变化事件
- WHEN 节流判定执行
- THEN 该 3 秒窗口内最多只发生一次截图
- AND 最多只出现一个确认悬浮窗

#### Scenario: 连续未命中的退避
- GIVEN 用户在微信聊天页停留，OCR 连续多次未识别到支付页面
- WHEN 又收到新的内容变化事件
- THEN 下一次允许截图的时间被推后到更长的间隔
- AND 不出现确认悬浮窗

#### Scenario: 窗口状态变化重置退避
- GIVEN 处于退避状态
- WHEN 前台窗口状态发生变化（切页或切换应用后回到微信）
- THEN 最小间隔恢复为初始值

#### Scenario: 用户点击翻页后按短间隔放行
- GIVEN 用户在微信内从聊天列表点进账单详情，该过程只产生内容变化事件
- WHEN 收到该点击事件，且其后的内容变化事件仍在持续到达
- THEN 换页信号被保留到判定执行时刻
- AND 本次判定按切页的短间隔放行，而不是走内容变化的长间隔

#### Scenario: 换页信号不被后续内容事件冲掉
- GIVEN 用户点击后微信连续发出多个内容变化事件
- WHEN 去抖把多次事件合并成一次判定
- THEN 判定拿到的仍然是「已换页」的结论
- AND 不出现「点击时放行、随后被长间隔拦下」导致的漏记

#### Scenario: 息屏与锁屏不截图
- GIVEN 屏幕已熄灭或设备处于锁屏状态
- WHEN 收到微信的内容变化事件
- THEN 不调用截图能力
- AND 不产生任何交易

#### Scenario: 非截图范围的应用不触发
- GIVEN 前台应用是支付宝或其他未受支持的应用
- WHEN 收到任意无障碍事件
- THEN 不调用截图能力

#### Scenario: 退避期内用户主动点击仍放行
- GIVEN 截图通道因连续未命中处于退避状态
- WHEN 用户在微信内点击进入支付成功页
- THEN 本次仍按切页间隔放行截图
- AND 支付页被正常识别并弹窗
- AND 退避计数在命中后归零

#### Scenario: 页面持续变化也能完成判定
- GIVEN 微信支付页持续产生内容变化事件（例如加载动画）
- WHEN 等待稳定判定
- THEN 判定在最长时间上限内执行，而不是被无限推迟
- AND 用户不需要额外操作就能看到弹窗

### Requirement: OCR 结果纠错与放弃判定
系统 SHALL 对 OCR 文本执行字符级归一化后，再交由现有的金额解析与页面判定。归一化 MUST 至少覆盖：全角数字与符号转半角、数字上下文中 `O`/`o`/`D` → `0`、`l`/`I` → `1`、`S` → `5`、`B` → `8`、紧邻数字的 `Y` → `¥`。

系统 MUST 在下列任一情况成立时放弃本次识别，且 MUST NOT 产生确认悬浮窗或交易：

- 归一化后仍无法通过严格金额格式校验
- 页面出现两个及以上互不相同的金额
- 页面没有任何支付成功 / 账单详情特征词
- 金额超出预设上限或为零

#### Scenario: 字母 O 误识别为数字零
- GIVEN OCR 输出的金额文本为「-42.OO」
- WHEN 归一化与解析执行
- THEN 金额被纠正为 42.00 元（4200 分）
- AND 触发确认悬浮窗

#### Scenario: 纠错后仍不合规则放弃
- GIVEN OCR 输出的金额文本为「¥4Z.5O」
- WHEN 归一化与解析执行
- THEN 不产生识别结果
- AND 在开启识别日志时记录「金额格式不合规」

#### Scenario: OCR 产生多个金额时放弃
- GIVEN 一次 OCR 在同一页面同时读出「¥25.50」与「¥3.00」
- WHEN 识别流程执行
- THEN 不出现确认悬浮窗
- AND 在开启识别日志时记录「金额歧义」

#### Scenario: 缺少支付特征词则放弃
- GIVEN OCR 文本里出现「¥25.50」但没有任何支付成功 / 账单详情特征词
- WHEN 识别流程执行
- THEN 不出现确认悬浮窗

### Requirement: 服务可靠运行与失效可见
系统 SHALL 尽最大可能让无障碍服务保持可用；当它确实失效时，系统 MUST 让用户**能发现**，而不是静默失效。

实现 MUST 满足：

- **服务连接过程 MUST NOT 被阻塞**：`onServiceConnected` 中 MUST NOT 同步执行创建窗口、
  初始化 UI 组合环境等重活。这类工作 MUST 放到主线程的后续循环执行，
  以避免触发系统的绑定超时（`wait for adding window timeout`）导致绑定被放弃。
- 自动记账总开关开启且用户已授权时，以**前台服务 + 常驻通知**维持进程优先级；
  通知 MUST 为低打扰（不发声、不弹横幅）
- 持续记录「最近一次收到受支持应用无障碍事件的时间」，并在设置页展示
- 超过设定阈值（30 分钟）无事件时，设置页 MUST 显示「疑似停止工作」状态，
  并提供跳转无障碍设置的一键入口
- 系统 MUST 实时监听无障碍授权的启停变化（`AccessibilityManager`），
  授权被撤销时发出可见告警，MUST NOT 等到用户下次进入设置页才发现
- 设置页 MUST 区分「从未授权」与「授权后被撤销」两种状态，后者 SHOULD 说明最可能的原因

系统 SHALL 提供降低被系统强制停止概率的手段：电池优化豁免的申请入口、
自启动引导、以及最近任务锁定引导。

系统 MAY 提供基于 Shizuku 的自动恢复（周期性巡检并把服务写回启用列表），
但该能力 MUST 在未安装 Shizuku 时安全降级，MUST NOT 影响其它功能。

上述机制 MUST NOT 申请 `INTERNET` 或任何网络能力；常驻通知 MUST NOT 承载任何网络内容。

#### Scenario: 服务连接不被自身阻塞
- GIVEN 无障碍服务刚被系统绑定
- WHEN `onServiceConnected` 返回
- THEN 悬浮窗预热等 UI 初始化在后台继续，不阻塞连接过程
- AND 系统不产生「wait for adding window timeout」
- AND 服务在启用列表中稳定保持

#### Scenario: 授权被撤销时立即可见
- GIVEN 应用进程存活，无障碍服务此前已授权
- WHEN 系统撤销了本应用的无障碍权限
- THEN 应用发出告警通知，说明自动记账已停止工作
- AND 通知可一键跳转到系统无障碍设置

#### Scenario: 设置页区分两种「未开启」
- GIVEN 无障碍服务当前不可用
- WHEN 用户打开设置页的自动记账区块
- THEN 若此前从未授权过，显示「去开启」引导
- AND 若此前授权过，显示「被系统关闭了」并说明可能是被从最近任务划掉

#### Scenario: 常驻通知可关闭且说明后果
- GIVEN 用户关闭了本应用的通知权限
- WHEN 进入设置页的自动记账区块
- THEN 提示通知关闭会导致失效时收不到提醒
- AND 自动记账的其他功能不被禁用

#### Scenario: 没有 Shizuku 时安全降级
- GIVEN 设备未安装 Shizuku 或未授予其权限
- WHEN 应用启动并执行保活相关逻辑
- THEN 所有 Shizuku 相关调用被跳过
- AND 自动记账与其它功能不受影响

#### Scenario: 仍然没有网络能力
- GIVEN 本变更实施完成
- WHEN 检查合并后的 AndroidManifest.xml
- THEN 不包含 `android.permission.INTERNET`
- AND 不包含任何 `ACCESS_NETWORK_STATE`、`CHANGE_NETWORK_STATE` 等网络相关权限

### Requirement: 节点与 OCR 双通道的兜底关系
系统 SHALL 把「无障碍节点文本」与「截图 OCR 文本」视为等价的两条文本来源，并在节点文本不可靠时由 OCR 兜底。

判定节点文本「可靠」MUST 同时满足：行数达到下限**且**总字符数达到下限。MUST NOT 只按行数判断。

即使节点文本被判为可靠，只要基于它的识别**未命中**，且 OCR 可用，系统 MUST 再尝试一次 OCR。

受支持应用 MUST NOT 被硬编码为「永不截图」——是否截图 MUST 依据「当前页面节点是否可靠」动态决定。

#### Scenario: H5 页面节点稀疏时由 OCR 兜底
- GIVEN 用户停留在支付宝账单详情页，该页为 H5，无障碍树只暴露「返回」「余额明细详情」等 3 个导航节点
- WHEN 识别流程执行
- THEN 判定节点文本不可靠，转而截图并走 OCR
- AND 识别出页面上真实存在的金额

#### Scenario: 节点丰富时不浪费截图
- GIVEN 用户停留在支付宝付款成功页，无障碍文本包含商户名、金额与状态
- WHEN 识别流程执行
- THEN 直接使用节点文本完成识别
- AND 不调用截图能力

#### Scenario: 节点判定失败后仍给 OCR 一次机会
- GIVEN 节点文本通过了「可靠」判据，但页面判定结果为未命中
- WHEN OCR 可用
- THEN 系统仍执行一次 OCR 识别
- AND 若 OCR 命中则正常弹窗

### Requirement: 金额解析必须排除非交易金额
系统 SHALL 在判断「页面是否只有一个金额」之前，先按**语义优先级**确定本次交易金额，
再对剩余的候选做排除，最后才判定歧义。

MUST 排除的情况：

- 本行或前后两行内出现「余额 / 可用余额 / 账户余额 / 零钱余额」——该数字是账户余额
- 前后两行内出现 `KB/s`、`℃` 等单位——该数字是状态栏读数
- 本行或紧邻行出现 `订单金额 / 商品金额 / 原价 / 优惠 / 立减金 / 已省 / 红包金额` 等标签
  ——这些是原价与优惠，不是本次实付金额
- 本行或紧邻行出现 `标价 / 汇率 / 外币 / 美元 / USD` 等外币信息
  ——微信外币支付页会同时出现「-42.00」（实付人民币）与「6.24美元」（标价）

「余额宝」MUST NOT 被当作余额标签（它是支付方式）。

当页面存在**带方向前缀的金额**（`支出X元` / `收入X元`）时，系统 MUST 以它为准，
MUST NOT 再因为它与其他数字共存而判歧义。

排除之后，若仍存在多个互不相同的金额且没有任何一个具备更高语义优先级，系统 MUST 放弃识别。

> 依据：真机实测支付宝「扫经营码付款」详情页同时出现 `订单金额 17500.00`、
> `工商银行立减金 -0.22` 与 `支出17499.78元`，旧逻辑判「金额歧义」永不记账。

#### Scenario: 订单金额与优惠不参与歧义判断
- GIVEN 支付宝详情页同时出现 `订单金额 17500.00`、`工商银行立减金 -0.22` 与 `支出17499.78元`
- WHEN 解析金额
- THEN 只有 `支出17499.78元` 被认定为交易金额
- AND 金额为 1749978 分
- AND 方向为支出

#### Scenario: 余额与状态栏数字不参与歧义判断
- GIVEN 支付宝账单页同时出现 `-25.00`（交易金额）、`¥217.01`（余额，上一行是「余额」）与 `5.24`（状态栏网速，相邻行有 `KB/s`）
- WHEN 解析金额
- THEN 只有 `-25.00` 被认定为交易金额
- AND 金额为 2500 分

#### Scenario: 余额宝不被当成余额
- GIVEN 付款成功页含「支付方式 余额宝」与金额 `¥25.50`
- WHEN 解析金额
- THEN `¥25.50` 仍被认定为交易金额

#### Scenario: 外币标价不参与歧义判断
- GIVEN 微信外币支付详情页同时出现 `-42.00`（实付）、`标价 6.24美元`、`汇率 1美元=6.72631人民币`
- WHEN 解析金额
- THEN 只有 `-42.00` 被认定为交易金额
- AND 金额为 4200 分

#### Scenario: 排除后仍歧义则放弃
- GIVEN 页面存在两个互不相同、且都没有方向前缀的金额，也没有任何可排除的上下文
- WHEN 解析金额
- THEN 判为金额歧义并放弃识别
- AND 不弹出确认悬浮窗

### Requirement: 主界面与列表页不触发识别
系统 SHALL 在判定页面不是**账单详情页**时跳过识别。

判定 MUST 采用正向准入而不是负向排除：页面必须**同时**满足下列条件才允许识别：

- 命中账单详情页标题（`账单详情` / `交易详情` / `余额明细详情` / `账单明细` 等）
  **或**命中 ≥ 2 个账单专属字段（`交易单号` / `商户单号` / `收单机构` / `清算机构` /
  `支付时间` / `收款时间` / `账单分类` / `对方账户` / `商品说明` 等）
- 不命中列表页判据（≥3 行「日期+时间」或 ≥2 个列表页专有文案）
- 不命中主界面 / 我的页专有入口词的组合

主界面与列表页的排除判据 MUST 保留，但只作为**辅助**：漏掉一个入口词时，
正向准入仍然能拦住误触发。MUST NOT 把「排除词表命中」当作唯一防线。

#### Scenario: 支付宝首页不误弹窗
- GIVEN 支付宝首页的「最近消息」区显示了历史通知「森众餐饮 付款成功 ¥25.00」
- WHEN 识别流程执行
- THEN 页面缺少账单详情页证据，不弹出确认悬浮窗

#### Scenario: 微信钱包页不误弹窗
- GIVEN 用户停在微信「钱包」页，页面上有「零钱 ¥426.20」「零钱通 收益率0.95%」
- WHEN 识别流程执行
- THEN 不弹出确认悬浮窗
- AND 不会把 ¥426.20 当成交易金额

#### Scenario: 支付宝「我的」页不误弹窗
- GIVEN 用户停在支付宝「我的」页，页面含「卡包」「账单」「总资产」「支付宝会员」
- WHEN 识别流程执行
- THEN 不出现确认悬浮窗

#### Scenario: 账单页不受排除词影响
- GIVEN 用户停在账单详情页，页面上含「查看更多」「转账」「联系商家」等常见文案
- WHEN 识别流程执行
- THEN 识别正常进行

### Requirement: 支付宝识别延迟
系统 SHALL 在支付宝支付结果页出现后，尽可能快地展示确认悬浮窗。

支付宝页面文本可读且内容完整时，识别 MUST 走无障碍节点路径，其延迟 MUST 明显低于截图 OCR 通道：从页面稳定到悬浮窗可见的处理耗时 MUST ≤ 250ms（不含事件去抖）。

无障碍节点文本足以判定页面时，系统 MUST NOT 触发截图或任何 OCR 相关开销。

#### Scenario: 支付宝付款成功页快速弹窗
- GIVEN 无障碍服务已开启，用户完成一笔支付宝付款并停留在「付款成功」页
- WHEN 结果页文本就绪
- THEN 悬浮窗在页面稳定后 250ms 内可见

#### Scenario: 节点够用时不碰 OCR

- WHEN 识别流程执行
- THEN 直接使用节点文本完成判定
- AND 不创建截图任务、不加载 OCR 模型

### Requirement: 识别延迟的可观测性
系统 SHALL 把一次识别的耗时按阶段暴露出来，使「慢在哪一段」可以被直接读出，而不是只能看到一个总数。

至少 MUST 暴露：节点采集耗时、截图耗时、文本行数、OCR 处理耗时、从命中到悬浮窗可见的耗时。

OCR 为整页一次推理时，MUST NOT 伪造「检测/识别」两段耗时数据；无意义的分段 MUST 以「不适用」呈现，而不是编一个数字。

#### Scenario: 设置页可读到分段耗时
- GIVEN 用户已完成至少一次识别
- WHEN 用户打开设置页的自动记账区块
- THEN 能看到最近一次的分段耗时与文本行数

#### Scenario: 识别日志含分段数据
- GIVEN 识别日志开关已开启
- WHEN 发生一次识别
- THEN 日志条目包含分段耗时与行数
- AND 不包含任何页面原文

### Requirement: 账单页强证据判定
系统 SHALL 要求「页面确实是账单详情页」有强证据才允许触发确认，MUST NOT 因为通用交易词汇凑数而命中。

强证据 MUST 取自下列之一：

- 页面标题类字段命中：「账单详情」「交易详情」「余额明细详情」「账单明细」
- 页面专属字段命中 ≥ 2 个：「交易单号」「商户单号」「订单号」「支付时间」「当前状态」「账单分类」「收单机构」「清算机构」「对方账户」「商品说明」「交易类型」「支付方式」「商家订单号」

系统的判定顺序 MUST 为：先排除主界面 / 我的页 / 列表页，再校验强证据，最后校验金额唯一性。

#### Scenario: 我的页不弹窗
- GIVEN 用户停在支付宝「我的」页，页面含「卡包」「账单」「总资产」「支付宝会员」「最近消息」等入口

- AND 不出现确认悬浮窗

#### Scenario: 账单列表页不弹窗
- GIVEN 用户停在微信账单列表页，页面上有多条交易的金额与日期
- WHEN 识别流程执行
- THEN 页面被判为列表页并排除
- AND 不出现确认悬浮窗

#### Scenario: 通用词凑数不算强证据
- GIVEN 页面只出现「交易」「订单」「支付方式」等通用词汇，没有任何账单专属字段
- WHEN 识别流程执行
- THEN 判为「不是支付页面」
- AND 不出现确认悬浮窗

#### Scenario: 发布版与 debug 构建行为一致
- GIVEN 分别安装 release（非 debuggable）与 debug 构建
- WHEN 用户停在同一张账单详情页
- THEN 两个构建都能识别并弹出确认悬浮窗
- AND 行为差异只出现在 debug 专属的模拟页面

### Requirement: 交易单号指纹与持久化去重
系统 SHALL 以「交易单号」作为同一笔账单的**长期**主指纹，并持久化「已提示」与「已忽略」两种状态。

**短窗口内的同一笔判定 MUST 由 [去重] 的会话层负责**，指纹层不再承担「挡住紧接着的第二次命中」的职责：
单号缺失或两页单号不一致（一有一无）是支付宝的常态，只靠指纹会漏掉跨页重复。

**系统 MUST NOT 通过模拟点击（如展开「更多」）来获取交易单号**：账本应用不得操作用户的其他应用界面。

无交易单号时，指纹 MUST 退化为「包名 + 金额 + 方向 + 商户名 + 账单时间」。
其中账单时间 MUST 使用解析出的账单时间而不是识别时刻 —— 支付宝的**旧版**账单详情布局
不渲染交易单号（25 张样本里有 21 张属于旧版），退化指纹是这个场景下的常态，
用它才能区分同商户同金额的不同笔。

单号字段的标签集 MUST 至少包含：`交易单号`、`商户单号`、`商家订单号`、`订单号`、**`转账单号`**。
微信的转账类账单用的正是「转账单号」，漏掉它会让转账类账单全部退化。

用户主动忽略或确认过的指纹 MUST 在 7 天内不再触发确认；指纹记录 MUST 仅存于本机。

#### Scenario: 支付宝无单号时按账单时间退化去重
- GIVEN 支付宝账单页不提供交易单号，账单时间为 2026-10-19 18:01:22，金额 2500 分，商户「森众餐饮」
- WHEN 用户忽略后再 10 秒重新打开同一张账单
- THEN 不出现确认悬浮窗

#### Scenario: 同商户同金额不同分钟视为两笔
- GIVEN 同一商户先后有两笔 17.00 元，账单时间分别为 17:59:40 与 18:01:22
- WHEN 两次识别完成
- THEN 各自弹出一次确认，互不去重

#### Scenario: 确认过的账单不重复入账
- GIVEN 用户对交易单号为 B 的账单点过「记一笔」
- WHEN 用户再次打开该账单
- THEN 不出现确认悬浮窗

#### Scenario: 不模拟点击对方界面
- GIVEN 支付宝账单页的交易单号需要展开「更多」才可见
- WHEN 识别流程执行
- THEN 系统不对支付宝界面执行任何点击操作
- AND 按退化指纹去重

### Requirement: 悬浮窗生命周期
系统 SHALL 让确认悬浮窗在用户离开触发页面后自动消失，MUST NOT 让一张残留卡片长期占用识别通道。

实现 MUST 满足：

- 用户点击「忽略」后立即隐藏，不需要等待超时
- 前台应用不再是触发它的受支持应用时，隐藏
- 受支持应用内页面标识变化（换页）时，隐藏
- 60 秒无操作时隐藏
- 悬浮窗存在期间 MUST NOT 阻塞采集与非确认类判定，但 MUST NOT 对同一指纹重复请求确认

#### Scenario: 忽略立即生效
- GIVEN 确认悬浮窗正在显示
- WHEN 用户点击「忽略」
- THEN 悬浮窗在一帧内消失
- AND 识别通道恢复正常工作

#### Scenario: 切走应用后自动隐藏
- GIVEN 确认悬浮窗在微信账单页上显示
- WHEN 用户按 Home 键回到桌面
- THEN 悬浮窗自动隐藏
- AND 不再持续占用识别

#### Scenario: 换页后自动隐藏
- GIVEN 确认悬浮窗在账单详情页上显示
- WHEN 用户在微信内点击返回，回到账单列表
- THEN 悬浮窗自动隐藏

### Requirement: 账单页识别延迟
系统 SHALL 在账单详情页稳定后尽快展示确认悬浮窗。

页面文本就绪到悬浮窗可见的处理耗时 MUST ≤ 350ms（不含事件去抖与截图节流等待），其中 OCR 推理 MUST ≤ 300ms。

微信通道采用两段式识别时，快筛那一段的耗时 MUST ≤ 180ms。

识别 MUST NOT 因为等待「页面完全静止」而丢弃已经截到的帧。

#### Scenario: 微信账单页 350ms 内弹窗
- GIVEN 无障碍服务已连接、OCR 已预热
- WHEN 用户点进微信账单详情页并停稳
- THEN 从页面稳定到悬浮窗可见 ≤ 350ms
- AND 分段耗时被写入设置页的 OCR 状态与识别日志

#### Scenario: 支付宝账单页不触发截图
- GIVEN 支付宝账单页的无障碍文本行数与字符数都达到可用阈值
- WHEN 识别流程执行
- THEN 直接使用节点文本完成判定
- AND 不调用截图能力

### Requirement: 账单详情页识别与字段提取
系统 SHALL 仅在用户停留在受支持应用（微信、支付宝）的**账单详情页**时触发识别，并从页面文本提取金额、收支方向、账单时间、可选的商户名与交易单号。

页面文本的来源有两条，对后续判定与解析**完全等价**：无障碍节点文本，以及当该来源不可用或不可靠时由截图 OCR 产出的文本。

「账单详情页」MUST 由页面专属证据证明，MUST NOT 仅凭通用交易词汇（如「交易」「订单」「金额」）认定。

系统 MUST NOT 在某一种账单类型识别失败后，转而尝试把页面当成另一种类型来记账。

系统 MUST 同时识别同一个应用的**多套账单详情布局**。真机实测支付宝存在两套：

| | 旧版（样本 00–20） | 新版（样本 21–24） |
|---|---|---|
| 页面标题 | 「账单详情」 | 无标题，只有关闭按钮 |
| 交易单号 | 折叠在「更多」里，默认不可见 | 直接展示，另有商户单号 |
| 金额无障碍文本 | `支出25元` 这类口语化文本 | 待补充实测 |
| 专属字段 | 支付时间 / 收单机构 / 清算机构 / 收款方全称 | 当前状态 / 支付时间 / 商品 / 商户全称 / 支付方式 |

识别规则 MUST NOT 假设「支付宝一定没有交易单号」或「一定用「支付时间」作时间标签」。

#### Scenario: 支付宝旧版布局
- GIVEN 支付宝旧版账单详情页，无障碍文本含「账单详情」「支出25元」「支付时间」「收单机构」
- WHEN 识别流程执行
- THEN 判为账单详情页
- AND 解析出金额 2500 分、方向支出

#### Scenario: 支付宝新版布局
- GIVEN 支付宝新版账单详情页，无障碍文本含「当前状态」「支付时间」「商户全称」「交易单号」「支付方式」
- WHEN 识别流程执行
- THEN 判为账单详情页（命中 ≥2 个专属字段，即使没有「账单详情」标题）
- AND 解析出金额与交易单号

#### Scenario: 微信转账类账单用「转账单号」
- GIVEN 微信「转账-来自群友」页，字段为「转账说明 / 转账时间 / 收款时间 / 转账单号」
- WHEN 提取交易单号
- THEN 得到 `转账单号` 后面的数字

#### Scenario: 支付宝支出账单
- GIVEN 无障碍服务已开启，用户停在支付宝某笔支出的账单详情页
- WHEN 页面文本含「账单详情」「森众餐饮」「支出25元」「交易成功」「支付时间 2026-10-19 18:01:22」
- THEN 解析出金额 2500 分、方向为支出
- AND 账单时间为 2026-10-19 18:01:22
- AND 来源标记为支付宝
- AND 触发确认悬浮窗

#### Scenario: 微信账单页走 OCR
- GIVEN 无障碍服务已开启，用户停在微信「账单详情」页，该页面对无障碍节点完全不可读（系统返回 null root）
- WHEN 截图 OCR 产出「美团」「-23.90」「当前状态」「支付成功」「支付时间」「2026年10月18日 20:10:02」「交易单号」「4500000576202610184019086744」
- THEN 解析出金额 2390 分、方向为支出
- AND 商户名为「美团」
- AND 交易单号为 `4500000576202610184019086744`
- AND 账单时间为 2026-10-18 20:10:02

#### Scenario: 页面不是账单详情页则不识别
- GIVEN 页面没有任何账单详情页专属证据
- WHEN 识别流程执行
- THEN 不出现确认悬浮窗
- AND 不产生交易

#### Scenario: 金额无法解析时静默跳过
- GIVEN 页面被判为账单详情页，但没有任何可解析的金额文本
- WHEN 识别流程执行
- THEN 不出现确认悬浮窗
- AND 在开启识别日志时记录一条「金额解析失败」

### Requirement: 金额形态与收支方向
系统 SHALL 从金额文本中解析**收支方向**，并把方向落成 `TransType`（收入 / 支出），MUST NOT 把方向信息丢弃后统一按支出入账。

必须支持的金额文本形态（均为真机实测文本）：

- 带中文方向前缀：`支出25元`、`支出29.74元`、`收入128.50元`
- 带符号且整行即金额：`-23.90`、`+128.50`
- 带货币符号：`¥25.50`、`￥25.50`
- 带「元」但无方向：`100元`

方向判定 MUST 按下列优先级依次尝试，命中即止：

1. 显式方向前缀（`支出` / `付款` / `收入` / `入账` / `收款` / `退款`）
2. 金额自身的正负号（`+` 为收入，`-` 为支出）
3. 页面状态词（`退款成功` / `已退款` / `已到账` 视为收入；`支付成功` / `交易成功` / `已支付` 视为支出）

三种都判定不出方向时，系统 MUST 放弃本次识别，MUST NOT 猜一个方向入账。

#### Scenario: 支付宝「支出25元」判为支出
- GIVEN 页面金额文本为「支出25元」
- WHEN 解析金额与方向
- THEN 金额为 2500 分
- AND 方向为支出

#### Scenario: 微信红包「+128.50」判为收入
- GIVEN 微信红包收款页的金额文本为「+128.50」
- WHEN 解析金额与方向
- THEN 金额为 12850 分
- AND 方向为收入
- AND 入账时写入一笔收入交易

#### Scenario: 正负号缺失时不猜方向
- GIVEN 金额文本为「100元」，页面上也没有任何可判定方向的词
- WHEN 解析金额与方向
- THEN 放弃识别
- AND 不出现确认悬浮窗

#### Scenario: 退款页判为收入
- GIVEN 支付宝退款详情页含「100元」「退款成功」「账单分类 退款」
- WHEN 解析金额与方向
- THEN 金额为 10000 分
- AND 方向为收入

### Requirement: 账单时间解析与记账日期
系统 SHALL 从账单详情页解析**这笔交易真实发生的时间**，并以它作为入账交易的 `occurredAt`，MUST NOT 用识别时刻冒充账单时间。

必须识别的时间字段标签：`支付时间`、`收款时间`、`交易时间`、`创建时间`、`转账时间`。

必须识别的时间文本格式：`2026-10-19 18:01:22`、`2026年10月18日 20:10:02`、`2026-10-19 18:01`。

标签与数值 MUST 允许被拆成两行（OCR 与节点树都会出现这种情况）。

时间解析失败时系统 MAY 回退为识别时刻，但 MUST 在识别日志中标注该笔为「时间回退」，MUST NOT 静默回退。

#### Scenario: 昨天支付的账单记在昨天
- GIVEN 用户今天（10-19）打开一笔账单，页面「支付时间」为 `2026-10-18 20:10:02`
- WHEN 用户确认记账
- THEN 该笔交易的 `occurredAt` 为 2026-10-18 20:10:02 对应的时刻
- AND 首页把它归到 10-18 这一组

#### Scenario: 跨月账单不落到本月
- GIVEN 页面「支付时间」为 `2026-09-28 09:12:00`
- WHEN 用户确认记账
- THEN 该笔交易落在 9 月，不影响 10 月统计

#### Scenario: 红包页用「收款时间」
- GIVEN 微信红包详情页的时间标签是「收款时间」，值为 `2026年10月15日 21:34:52`
- WHEN 解析账单时间
- THEN 得到 2026-10-15 21:34:52

#### Scenario: 解析不出时间时明确标注回退
- GIVEN 页面没有任何可识别的时间字段
- WHEN 识别完成且用户确认记账
- THEN 使用识别时刻作为 `occurredAt`
- AND 识别日志中该条标注「时间回退」

### Requirement: 页面自带分类到账本分类的映射
系统 SHALL 在账单页提供分类信息时，把它映射到账本的分类，作为确认悬浮窗的预选分类。

支付宝 `账单分类`（如「餐饮美食」「数码电器」「退款」）与微信交易类型 MUST 通过一张显式映射表映射到账本分类名。

映射不到时 MUST 回退到现有默认分类逻辑，MUST NOT 因为映射失败而放弃整个识别。

#### Scenario: 用页面分类预选
- GIVEN 支付宝账单页「账单分类」为「餐饮美食」，账本里有同名分类
- WHEN 悬浮窗展示
- THEN 分类预选为「餐饮美食」

#### Scenario: 映射不到时回退
- GIVEN 页面分类为「网络购物」，账本里没有对应分类
- WHEN 悬浮窗展示
- THEN 分类回退为设置里的默认分类

### Requirement: 识别结果不因弹窗失败而丢失
系统 SHALL 把「识别成功」与「用户看到确认卡片」解耦。

部分系统对支付类应用有「支付保护」，禁止在其界面上显示悬浮窗。识别成功但弹窗失败时，
系统 MUST 把该笔落成一条**待确认账单**并保留，MUST NOT 因为弹窗失败而丢弃识别结果。

待确认账单 MUST 在下列通道中至少一处可被发现：常驻通知上的待确认计数、应用内首页的待确认入口。

待确认账单 MUST 有明确的生命周期：用户确认后转为正式交易，用户忽略或超过保留期后失效。

#### Scenario: 支付保护导致弹窗失败
- GIVEN 用户停在支付宝账单页，系统禁止第三方悬浮窗显示
- WHEN 识别成功但悬浮窗无法显示
- THEN 该笔仍被保存为待确认账单
- AND 常驻通知或首页入口能看出有 1 条待确认

#### Scenario: 当时没空，之后补确认
- GIVEN 已有一条待确认账单
- WHEN 用户一小时后打开本应用
- THEN 能在待确认列表里看到它并完成确认
- AND 入账时间仍然是账单上的时间，不是确认时刻

#### Scenario: 忽略后不再出现
- GIVEN 待确认列表里有一条记录
- WHEN 用户忽略它
- THEN 它从列表消失
- AND 同一张账单不会再被重新生成

### Requirement: 回到应用时自动恢复无障碍授权
系统 SHALL 在用户回到应用时检查无障碍服务是否仍在启用列表，若不在则尝试恢复。

恢复手段按可用性递进：

1. 已授予 `WRITE_SECURE_SETTINGS` 时，直接把本服务写回
   `enabled_accessibility_services`；
2. 未授予时，展示一键跳转系统无障碍设置的入口，并在设置页给出获取该权限的 `adb` 命令。

系统 MUST NOT 在用户主动关闭自动记账总开关后自动把它打开。

#### Scenario: 被系统关掉后回到应用自动修好
- GIVEN 无障碍服务被系统从启用列表移除，且已授予 `WRITE_SECURE_SETTINGS`
- WHEN 用户打开本应用
- THEN 服务被重新写回启用列表
- AND 设置页显示已恢复

#### Scenario: 没有写设置权限时给出口
- GIVEN 未授予 `WRITE_SECURE_SETTINGS`
- WHEN 服务被发现不在启用列表
- THEN 设置页展示一键跳转入口与获取权限的 adb 命令
- AND 不假装已修复

#### Scenario: 用户主动关闭后不自作主张
- GIVEN 用户在本应用内关闭了自动记账总开关
- WHEN 用户下次打开应用
- THEN 系统不会自动重新开启无障碍服务

### Requirement: 确认悬浮窗展示方向与时间
系统 SHALL 在确认悬浮窗上展示识别出的**方向（收入/支出）**与**账单时间**，使用户在确认前就能发现方向或日期错误。

方向 MUST 可在悬浮窗内切换（收入 ↔ 支出）；切换后入账 MUST 使用用户选定的方向。

#### Scenario: 悬浮窗显示账单日期
- GIVEN 识别到账单时间为 10-18 20:10
- WHEN 悬浮窗展示
- THEN 卡片上可见「10月18日 20:10」

#### Scenario: 用户当场把方向改掉
- GIVEN 识别结果为收入 128.50
- WHEN 用户把方向切到支出并点「记一笔」
- THEN 写入一笔支出 12850 分

### Requirement: 无障碍事件开销与功耗控制
系统 SHALL 把无障碍事件的系统级与进程级开销压到最低，MUST 满足：

- 服务配置 MUST 声明 `packageNames` 白名单，只接收受支持应用的包（debug 构建可另含自身包名）。
  这从系统侧过滤事件，是本变更最有效的一项省电措施。
- 服务 MUST NOT 订阅与本功能无关的事件类型；`TYPE_VIEW_CLICKED` 只用于识别换页，
  MUST NOT 因它触发任何 IO 或截图。
- `onAccessibilityEvent` MUST NOT 在每次事件上创建协程、创建对象或执行磁盘读写；
  去抖 MUST 用「记录时间戳 + 单一调度」实现，滚动时不得产生每事件一次的对象分配。
- 息屏、锁屏、自动记账总开关关闭时，MUST 不产生任何截图、OCR 或数据库访问。
- `flagRetrieveInteractiveWindows` 与 `flagIncludeNotImportantViews` 若保留，
  MUST 有明确用途说明；不得同时无条件开启而无收益。

#### Scenario: 非受支持应用的事件不进进程
- GIVEN 用户在浏览器里快速滚动产生大量内容变化事件
- WHEN 检查应用进程的 CPU 占用
- THEN 应用不因这些事件产生可测量的 CPU 开销
- AND 不会出现本应用的事件处理日志

#### Scenario: 长时间浏览不产生协程风暴
- GIVEN 用户在微信聊天列表连续滑动 60 秒
- WHEN 观察识别的去抖行为
- THEN 不会为每个事件创建新的调度任务
- AND 应用不出现可感知的发热

#### Scenario: 息屏后零工作
- GIVEN 屏幕熄灭或设备锁屏
- WHEN 受支持应用在后台产生无障碍事件
- THEN 不调用截图能力
- AND 不执行 OCR
- AND 不查询数据库

### Requirement: 无感化（无障碍图标与通知）
系统 MUST NOT 声明 `FLAG_REQUEST_ACCESSIBILITY_BUTTON`，因为它的副作用是在系统界面显示
无障碍快捷按钮/图标。用户明确要求界面上不出现该图标。

服务 MUST 在系统允许的版本上声明 `android:isAccessibilityTool="true"`，表明本服务是
真正的辅助工具用途（与 GKD 等成熟无障碍应用一致）。

保活 MUST 改用其余手段实现（前台服务、授权状态监听、周期巡检），
MUST NOT 因此退化为「静默失效」——失效可见性由既有 Requirement 保证。

状态栏上由系统绘制的「无障碍已启用」小图标不受应用控制，设置页 MUST 如实说明这一点，
MUST NOT 让用户误以为应用还有可关闭的图标没有关。

常驻通知 MUST 属于低打扰通道：不发声、不振动、不弹横幅、不显示角标，
且用户关闭通知权限时 MUST NOT 影响识别功能。

#### Scenario: 开启后界面上没有无障碍图标
- GIVEN 用户开启了本应用的无障碍服务
- WHEN 返回桌面或任意应用
- THEN 屏幕边缘与导航栏不出现本应用的无障碍按钮/图标

#### Scenario: 通知不打扰
- GIVEN 自动记账处于开启状态
- WHEN 用户停留在任意应用
- THEN 常驻通知不发声、不振动、不弹横幅、不显示角标

#### Scenario: 关闭通知后仍能识别
- GIVEN 用户在系统设置里关闭了本应用的通知权限
- WHEN 用户停在账单详情页
- THEN 确认悬浮窗仍能正常出现
- AND 设置页提示「通知关闭后失效时收不到提醒」

### Requirement: 微信通道两段式识别提速
系统 SHALL 在微信通道（节点不可读、必须 OCR）采用**两段式识别**：先对屏幕上半部分做一次整页 OCR 快筛，
只有在快筛命中账单页特征时才继续识别下半部分。

这与既有的「禁止检测+逐行两阶段方案」约束不冲突：两段共用同一个整页推理模型，区别只在裁剪区域。

快筛区域 MUST 覆盖所有已知账单类型的关键字段（商户、金额、状态、时间）。
快筛未命中时 MUST 直接放弃本次识别，不执行完整页 OCR。

快筛阶段 MUST NOT 因为区域裁剪而丢失方向信息。

#### Scenario: 微信账单页先快筛再提字段
- GIVEN 用户点进微信某张账单详情页
- WHEN 识别流程执行
- THEN 先对上半屏做一次 OCR
- AND 命中账单特征后才处理其余区域
- AND 从页面稳定到悬浮窗可见的总耗时优于整页一次性 OCR

#### Scenario: 非账单页不做整页 OCR
- GIVEN 用户停留在微信聊天页
- WHEN 快筛 OCR 未命中账单特征
- THEN 不再执行完整页 OCR
- AND 不出现确认悬浮窗

### Requirement: 识别结果的可观测性扩展
系统 SHALL 在识别日志中记录足以复现判断的字段：方向、账单时间、以及「时间是否回退」标记，
MUST NOT 记录完整页面原文。

#### Scenario: 日志能区分方向与时间来源
- GIVEN 识别日志开关已开启
- WHEN 完成一次识别
- THEN 该条日志包含方向（收入/支出）与账单时间
- AND 时间来自回退时该条标注「时间回退」

### Requirement: 商户名（备注）提取
系统 SHALL 从账单页提取**商户实体名**作为确认卡片的商户展示与入账备注。

候选来源与优先级：

1. 商户字段标签的值：`收款方全称`、`商户全称`、`收款方`、`商户名称`、`商家名称`、`对方账户`、`商户简称`
2. 金额所在视觉行的邻近行中，**单个 cell** 级别的文本（MUST NOT 直接使用整行拼接结果）
3. 取不到时返回「无商户」，MUST NOT 编造或使用占位文案

系统 MUST 排除下列文本，即使它们出现在金额邻近行：

- 操作/按钮类文案及其描述：`返回`、`按钮`、`回首页`、`返回商家`、`完成`、`确定`、`忽略`、`参与`、`去参与`、`一键领`、`查看详情`、`联系商家` 等
- 页面活动/广告文案：`支付有礼`、`红包`、`体验金`、`账单贴纸`、`碰友节`、`去参与` 等
- 多个按钮被拼进同一行的文本（含「按钮」「回首页」「返回商家」等片段的整行）

商户名仍 MUST NOT 参与去重指纹。

备注落库规则：商户名存在时写入备注；取不到时备注 MUST 为空字符串，MUST NOT 写入「未识别到商户」「无」这类占位文字。

#### Scenario: 支付成功页取到真实商户
- GIVEN 支付宝支付成功页含「杭州深度求索」「支付成功」「¥20.00」「完成」
- WHEN 提取商户名
- THEN 商户为「杭州深度求索」
- AND 备注为「杭州深度求索」

#### Scenario: 按钮文案不当商户
- GIVEN 页面金额邻近行是「回首页 返回商家」与「返回 按钮」
- WHEN 提取商户名
- THEN 这些文本都不被当作商户
- AND 若没有其它可用的商户字段，商户为「无商户」

#### Scenario: 取不到商户时备注为空
- GIVEN 页面没有任何可用的商户实体名
- WHEN 用户确认入账
- THEN 该笔交易的备注为空字符串
- AND 备注里不出现「未识别到商户」之类的占位文字

### Requirement: 授权状态实时可见
系统 MUST 让设置页的自动记账区块及时反映无障碍授权的真实状态，MUST NOT 出现「其实已经开启了还显示未开启」的长期滞后。

实现 MUST 满足：

- 监听 `AccessibilityManager` 的全局状态变化与（API 33+）服务级状态变化，收到变化后立即重算并刷新界面
- 应用回到前台（`ON_RESUME`）时立即重算
- 在「未开启」状态且用户刚从授权页返回时，MUST 以短间隔（≤1 秒）复检若干次（覆盖系统启用列表的延迟），一旦检到已开启立即转为已开启，无需用户手动切页
- 状态刷新 MUST NOT 以伪造方式呈现：检不到就继续显示未开启，不得先乐观显示为已开启

#### Scenario: 从系统设置开启后回到应用立即变绿
- GIVEN 设置页显示「无障碍服务未开启」
- WHEN 用户跳转系统无障碍设置开启本服务并返回应用
- THEN 2 秒内该行变为「无障碍服务已开启」
- AND 不需要用户切走再回来

#### Scenario: 授权被撤销时立即提示
- GIVEN 服务此前已开启，设置页显示已开启
- WHEN 系统撤销了本应用的无障碍授权（应用处于前台设置页）
- THEN 该行在 2 秒内变为未开启并给出原因说明

#### Scenario: 检不到时如实显示
- GIVEN 用户并未开启无障碍服务
- WHEN 用户在设置页停留
- THEN 状态一直是「未开启」
- AND 不会先显示已开启再退回

### Requirement: 支付结果页不参与入账
系统 MUST NOT 把「支付成功 / 付款成功 / 交易成功」这类**支付结果页**当成账单详情页入账。

结果页判据 MUST 同时满足：

- 页面命中成功类状态词（`支付成功` / `付款成功` / `交易成功` / `支付完成` / `付款完成`）
- **没有**账单标题（`账单详情` / `交易详情` / `余额明细详情` / `账单明细` 等）
- **没有**任何交易单号（`交易单号` / `商户单号` / `商家订单号` / `转账单号` / `订单号`）
- **没有**任何账单时间字段（`支付时间` / `收款时间` / `交易时间` / `转账时间` / `创建时间`）

任一条件不满足就 MUST NOT 判为结果页。

> 依据：2026-10-20 真机，一笔 20.00 元支付宝付款先出现「付款成功（聚合收款）」页、
> 随后出现「支付成功」页；后者能凑够「付款方式 / 当前状态」两个强字段，因此被当成账单详情页
> 又识别了一次。结果页不入账之后，同一笔付款只在真正带账单信息的那一页触发。
>
> 判据保守的原因：支付宝旧版账单详情页在 25 张样本里有 21 张不渲染交易单号，
> 若只按「无单号」排除会大面积漏记；它们一定有「支付时间」，所以用时间字段作为放行依据。

#### Scenario: 支付宝支付成功页不弹窗
- GIVEN 页面文本为「支付成功 / ¥20.00 / 杭州深度求索 / 付款方式 / 账户余额 / 当前状态 / 完成」
- WHEN 识别流程执行
- THEN 判为支付结果页
- AND 不出现确认悬浮窗
- AND 识别日志记录「支付结果页，不入账」

#### Scenario: 结果页带交易单号仍按账单入账
- GIVEN 微信页面为「当前状态 / 支付成功 / ¥25.50 / 瑞幸咖啡 / 交易单号 4500…」
- WHEN 识别流程执行
- THEN 正常判为账单详情页并弹窗

#### Scenario: 旧版账单不因缺单号被误杀
- GIVEN 支付宝旧版账单页为「账单详情 / 天猫 / 支出25元 / 交易成功 / 支付时间 2026-10-19 18:01:22 / 付款方式」
- WHEN 识别流程执行
- THEN 仍判为账单详情页并弹窗

#### Scenario: 同一笔付款跨两页只记一次
- GIVEN 一笔付款在「聚合收款」与「支付成功」两页先后出现
- WHEN 两页先后被识别
- THEN 结果页不触发
- AND 账单页最多弹一次确认
