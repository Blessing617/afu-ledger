# data-safety

## Purpose

保障用户账本数据在「升级应用」「换设备」「误操作」之后不丢失：升级是覆盖安装而非重装，数据可导出成轻量备份文件并随时导回。

## Requirements

### Requirement: 覆盖安装不丢数据

系统 SHALL 在用户安装新版本 APK 时保留全部账单、账户、分类、分类图标与定时规则。

- 同一应用的 release 包 MUST 使用固定签名（项目 keystore），使系统更新与 `adb install -r` 都是覆盖安装，不触发卸载。
- 该 keystore MUST 不提交进仓库；仓库只提供 `keystore.properties` 的模板，缺失时构建回退到 debug 签名并在构建日志中警告。
- 包名 `com.afu.ledger` MUST 保持不变（包名变化等于换应用，数据必然丢失）。

#### Scenario: 从旧版本覆盖升级

- GIVEN 设备上已安装 0.7.0，有 100 笔账单、3 个账户、若干定时规则
- WHEN 用户安装 1.0.0 release 包（同签名）
- THEN 应用正常启动
- AND 账单、账户、余额、分类、定时规则全部保留
- AND 不出现「数据已清空」或「需要重新初始化」的提示

#### Scenario: 签名不一致时明确失败

- GIVEN 设备上已安装的包由旧 keystore 签名
- WHEN 用户安装由新 keystore 签名的包
- THEN 系统拒绝安装（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）
- AND README 的升级说明写清楚「换签名必须先导出备份再卸载重装」

### Requirement: 数据库迁移可用且被测试

系统 SHALL 在每次数据库版本变化时提供迁移，并保留全部历史数据。

- 数据库 MUST NOT 使用 `fallbackToDestructiveMigration`。
- 每个新增的 schema 版本 MUST 随仓库提交导出的 schema JSON。
- MUST 有自动化迁移测试覆盖「上一版本 → 当前版本」，验证迁移后表结构与数据都完整。

#### Scenario: 迁移测试通过

- GIVEN 仓库内存在 schema v2 与 v3 的 JSON
- WHEN 运行迁移测试
- THEN 用 v2 建库并写入样例数据后打开 v3
- AND 所有表存在，样例数据可读出，余额计算正确

#### Scenario: 迁移失败不静默清空

- GIVEN 数据库文件损坏或迁移抛异常
- WHEN 应用启动并打开数据库
- THEN 应用捕获异常并提示用户（例如「数据读取失败，请联系作者并附上导出备份」）
- AND MUST NOT 删除或清空原数据库文件

### Requirement: 导出本地备份

系统 SHALL 允许用户把全部账本数据导出为单个备份文件，并保存到用户通过系统文件选择器指定的位置。

- 备份内容 MUST 包含：格式版本、导出时间、应用版本、账户（含初始余额、类型、颜色、图标、归档状态、排序）、分类（含图标、颜色、排序）、交易（含金额、收支类型、分类、账户、备注、时间、来源）、定时规则（含周期、期次、结束条件、启用状态）。
- 备份格式 MUST 为 UTF-8 JSON，可被人直接阅读。
- 导出 MUST 流式写入，内存占用不随记录数增长：账户、分类、交易、规则逐表读取并写入，不得把整表一次性加载为 List。
- 备份文件 MUST NOT 包含任何设备标识、账号信息或无网络权限以外的隐私内容。
- 导出成功 MUST 展示文件保存位置与条数统计。

#### Scenario: 导出全部数据

- GIVEN 账本内有 5000 笔交易、4 个账户、20 个分类、3 条定时规则
- WHEN 用户点「导出备份」并在系统选择器里选好位置
- THEN 生成 `.json` 备份文件
- AND 文件包含全部 5000 笔交易与其它实体
- AND 导出完成后提示「已导出 5000 笔交易」及文件路径

#### Scenario: 取消保存不产生空文件

- GIVEN 用户点「导出备份」
- WHEN 用户在系统文件选择器里按返回取消
- THEN 不创建任何文件
- AND 界面回到设置页且没有错误提示

### Requirement: 导入备份并还原

系统 SHALL 允许用户从备份文件还原账本数据。

- 导入 MUST 先校验文件格式与格式版本；不支持的版本 MUST 拒绝并说明原因，不得部分导入。
- 导入 MUST 在一个数据库事务内完成「清空现有数据 + 写入备份数据」，任一步失败则整体回滚。
- 导入 MUST 要求用户二次确认，并明确提示「现有数据将被替换，建议先导出当前数据」。
- 导入成功 MUST 展示还原的账户、分类、交易、规则条数。

#### Scenario: 换机还原

- GIVEN 用户在新设备上装了同版本应用，账本为空
- WHEN 用户选择此前导出的备份文件并确认导入
- THEN 账户、分类、交易、定时规则全部出现
- AND 各账户余额与导出前一致
- AND 首页今日支出与导出前一致

#### Scenario: 版本不兼容被拒绝

- GIVEN 备份文件的格式版本号高于应用支持的版本
- WHEN 用户尝试导入
- THEN 提示「备份文件来自更新版本的应用，请先升级」
- AND 现有数据完全不变

#### Scenario: 文件损坏时回滚

- GIVEN 用户选择了一个被截断的 JSON 文件
- WHEN 用户确认导入
- THEN 解析失败并提示文件损坏
- AND 现有数据完全不变

### Requirement: 数据管理入口

系统 SHALL 在设置页提供「数据管理」区块，展示当前数据量与备份入口。

- 区块 MUST 显示：交易条数、账户数、数据库文件大小（KB/MB）。
- 区块 MUST 提供：导出备份、导入备份、清空全部数据。
- 「清空全部数据」MUST 二次确认（文案明确「将删除全部账单，且不可撤销」），成功后账本回到首次使用状态。
- 数据管理区块 MUST 不新增常驻后台任务与网络请求。

#### Scenario: 查看数据量

- GIVEN 账本有 1234 笔交易
- WHEN 用户打开设置页
- THEN 数据管理区块显示「1,234 笔交易」与数据库大小

#### Scenario: 清空全部数据

- GIVEN 账本内有交易、账户、分类、定时规则
- WHEN 用户点「清空全部数据」并在确认框点「确认清空」
- THEN 首页显示首次使用的空状态
- AND 账户、分类、规则全部清空
- AND 已设置的自动记账开关与主题设置保留（它们不属于账本数据）
